The single sentence to hold onto. Separate compute from data layout. Executors provide task slots; partitions define units of work; stages are separated by shuffle boundaries; and Delta makes cloud files transactional and versioned. Almost every question below is a detail of that sentence.

1 The whole picture: submit → output

The execution chain. Everything in this document is a detail of one of these boxes.

Why laziness matters. The driver does not execute transformations as you write them. It accumulates a plan. Only when an action demands materialisation does Spark optimise the whole chain at once and turn it into executable work. That is what lets Catalyst push filters into the scan, prune columns, and reorder operations before a single byte is read.

The three layers to name in an interview

DriverPlans and schedules. Holds the DAG, task metadata, broadcast metadata.
PartitionsData-level parallelism. Logical units of work.
Executor coresCompute-level parallelism. Task slots.

2 Driver, worker, executor, core

The mistake that costs interviews. Executor sizing does not decide that "executor 1 owns the first chunk of the file". Compute capacity and partition layout are separate concerns. The scheduler can run the task for any partition on any suitable free executor.
Interview answer. "The driver coordinates; executors compute; cores provide concurrency; partitions are logical units of data and are not permanently attached to executors."

3 How 1 TB in S3 becomes input partitions

Why not load the 1 TB first? Distributed systems move computation to independently readable pieces of data. Each task reads only the bytes it needs, transforms those rows, and emits output or shuffle data. Thousands of tasks proceed in parallel and no single executor ever holds the whole dataset.

The four meanings of "partition" — the reason this gets confusing

TermWhen it appearsWhat it is
Input partitionsScan planning, before readingLogical chunks of source data that become read tasks
DataFrame partitionsAs transformations define a datasetLogical divisions of that dataset
Shuffle partitionsAt a wide operation / ExchangeNew buckets created by redistributing across the cluster
Output partitionsDuring writePhysical files and directory partitions — not the same as task partitions

4 Partition → task → core, and waves

5 partitions, 4 cores: four tasks run immediately, the fifth waits for a free slot.

Waves. Total tasks ÷ total cores = number of waves. 4,000 partitions on 200 cores is 20 waves. This is why partition count matters: too few and cores sit idle; too many and per-task overhead (a few ms each) dominates. Target 2–4× your core count, or roughly 128 MB of data per task.
Q: Does an executor split its data into tasks? No — backwards. The driver creates one task per partition, then schedules those tasks onto free executor cores. A partition never contains multiple tasks within the same stage.

5 Jobs, stages, DAG, and the shuffle boundary

Narrow vs wide

NarrowWide
filter select map withColumn groupBy orderBy distinct repartition most joins
Output partition depends on limited input partitions Output partition depends on data from many input partitions
No network redistributionRequires shuffle / Exchange
Pipelines into the same stageCreates a stage boundary
"Wide" means the dependency crosses partition boundaries. It does not mean "many columns were selected". This misconception is common and immediately audible in an interview.

Why a shuffle is expensive — six separate costs

  1. Serialization — every record converted to bytes
  2. Disk — map tasks write shuffle files locally; a full write plus a full read
  3. Network — reduce tasks fetch from every map task (all-to-all)
  4. Memory — sort/hash structures on both sides, spilling if they exceed execution memory
  5. Synchronisation — a stage barrier; one straggler stalls everything
  6. Fault cost — losing an executor loses its shuffle output, forcing upstream re-runs

6 groupBy across executors

This is the section that confuses people most. Follow the data for df.groupBy("region").sum("amount").

Q: Why is groupBy a wide transformation? "Because the same key can exist in many input partitions. Spark computes partial aggregates locally, then redistributes those partials by key so that all values for a key land in one partition, where the final aggregate is computed."

7 Delta table anatomy and _delta_log

The mental model. Delta = Parquet + a folder of JSON commits. To read version N, Spark replays commits 0…N (or the latest checkpoint plus the remainder) to compute the active file set, then reads exactly those Parquet files. Nothing proprietary — delete _delta_log and you still have readable Parquet, you just lose ACID and history.
Q: Is _delta_log per row or per customer ID? Neither. It belongs to the whole table. It records file-level actions, not row-level ones.

What the log buys you over plain Parquet

Plain Parquet folderDelta table
"The table" = whatever files are presentThe log names exactly which files are current
A failed write leaves half-written garbage visibleCommits are atomic — readers never see partial writes
No UPDATE / DELETE / MERGEFull DML support
No historyTime travel by version or timestamp
Schema drift silently corruptsSchema enforced on write

8 MERGE / upsert on immutable files

The question everyone gets asked: "Parquet files are immutable. So how does Delta update a single row?" Answer: it doesn't. It rewrites the file containing that row and commits a new version that points at the replacement.
MERGE INTO customers AS t
USING updates AS s
  ON t.customer_id = s.customer_id
WHEN MATCHED AND s.op = 'delete' THEN DELETE
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
WHEN NOT MATCHED BY SOURCE THEN UPDATE SET t.is_active = false;
Performance rule. MERGE cost is driven by how many files must be rewritten. Add a partition or Z-Order predicate on the join key so Delta can skip files it does not need to touch: ON t.id = s.id AND t.event_date >= current_date() - 7.

9 Time travel, SCD1 and SCD2

SELECT * FROM customers VERSION AS OF 4;
SELECT * FROM customers TIMESTAMP AS OF '2026-08-08 09:00:00';
DESCRIBE HISTORY customers;
RESTORE TABLE customers TO VERSION AS OF 4;

Time travel works because remove is logical. Delta computes the active file set for the requested version and reads those files — which still exist until VACUUM deletes them.

Time travel is bounded by VACUUM retention (default 7 days). It is a system recovery feature, not a substitute for modelling business history.

Time travel vs SCD2 — the distinction interviewers probe

Time travelSCD Type 2
Whose historySystem — the table as it wasBusiness — the entity as it was
Stored whereOld files + logExtra rows in the current table
Survives VACUUMNoYes
Answers"What did the table look like Tuesday?""What was this customer's tier in March?"

10 Small files, OPTIMIZE, VACUUM, Z-Order

Why small files hurt — four separate costs

1. ListingThe driver enumerates every file. On S3 this is paginated API calls and can take minutes with the cluster idle.
2. Task overheadOne task per file — thousands each doing milliseconds of real work.
3. MetadataEvery Parquet file has a footer. With tiny files the footer can exceed the data.
4. CompressionDictionary and RLE encodings need volume to be effective.

Target 128 MB – 1 GB per file. Also: every small file adds an add action to _delta_log, so the log itself grows and snapshot reconstruction slows.

The three maintenance commands

OPTIMIZE customers;                                  -- compact small files
OPTIMIZE customers ZORDER BY (customer_id, region);  -- compact + co-locate
VACUUM customers RETAIN 168 HOURS;                   -- delete unreferenced files
CommandDoesDoes NOT
OPTIMIZERewrites many small files into fewer big onesDelete anything; old files remain for time travel
ZORDERCo-locates similar values so min/max stats become selectiveHelp columns you don't filter on
VACUUMPhysically deletes files no longer referencedTouch active files
VACUUM destroys time travel beyond its retention window. Default and minimum safe retention is 7 days — it exists so that in-flight readers and writers are not pulled out from under. Lowering it requires explicitly disabling a safety check, and doing so during concurrent writes can corrupt readers.

Data skipping — how ZORDER actually helps

Liquid clustering is the newer alternative: CLUSTER BY (col) at table creation. Unlike Z-Order it can be changed later without rewriting the whole table, and it handles skew better.

11 Joins, skew, and AQE

The three strategies

StrategyMechanismCost
Broadcast hashSmall side collected to driver, shipped to all executors, big side streams locallyNo shuffle on the big side. Needs driver + executor memory for the copy.
Sort-mergeBoth sides shuffled by key, sorted within partitions, merged2 shuffles + 2 sorts. Scales to any size.
Shuffle hashBoth shuffled; hash table built per post-shuffle partitionShuffle, no sort.
Broadcast passes through the driver. A 2 GB broadcast needs 2 GB of driver heap plus 2 GB on every executor. Broadcasts cause driver OOM, not only executor OOM. And broadcast() is a hint — Spark ignores it for FULL OUTER joins. Always verify BroadcastHashJoin in the plan.

AQE — what it changes at runtime

Coalesce shuffle partitionsMerges tiny post-shuffle partitions after seeing real sizes. This is what makes the default 200 survivable.
Switch join strategyFlips sort-merge → broadcast when a side turns out small after runtime filtering.
Split skewed partitionsSplits an oversized partition and replicates the matching side. Requires exceeding both the factor and the byte threshold.
Why AQE can exist at all: a shuffle already forces a materialisation barrier. The same property that makes shuffle expensive is what gives Spark a moment to look at real statistics and re-plan. Cost and opportunity are the same mechanism.

13 Auto Loader, streaming, checkpoints

(spark.readStream.format("cloudFiles")
   .option("cloudFiles.format", "parquet")
   .option("cloudFiles.schemaLocation", f"{path}/_schema")
   .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
   .load(raw_path)
   .withColumn("_ingest_ts", F.current_timestamp())
   .withColumn("_source_file", F.col("_metadata.file_path"))
 .writeStream
   .option("checkpointLocation", f"{path}/_ckpt")
   .trigger(availableNow=True)        # process all available, then STOP
   .toTable("bronze_events"))
trigger(availableNow=True) is the underused one. You get streaming semantics — checkpointed, exactly-once file handling — with batch execution. Use it instead of a scheduled batch job whenever the source is an append-only directory. Re-running processes only new files.
Q: Does Spark give exactly-once? "Exactly-once processing internally, via checkpointed offsets and deterministic replay. End-to-end additionally needs a replayable source and an idempotent or transactional sink. The standard hook is foreachBatch with the batchId — a MERGE keyed on it makes retries safe. Writing to a REST API is at-least-once no matter what Spark does."

Watermarks

.withWatermark("event_time", "10 minutes")
.groupBy(F.window("event_time", "1 hour"), "device_id").agg(...)

Two effects: it bounds how long window state is retained, and in append mode it decides when a window is emitted. Too long → unbounded state → the job OOMs after days. Too short → late data silently dropped. Monitor numRowsTotal in stateOperators; monotonic growth predicts a failure weeks in advance.

14 Debugging: a 20-minute job now takes 2 hours

Follow this order. Reversing it is what a weak engineer does.
  1. Compare inputs. Input bytes and file count versus a known-good run. Did the source triple? Did someone start writing 400,000 tiny files?
  2. Find the slow stage. Jobs → Stages. Where is wall-clock time actually spent?
  3. Read the physical plan. Did a broadcast join silently become a sort-merge join because the "small" side grew past the threshold? This is the single most common cause of a sudden regression.
  4. Task duration distribution. Summary Metrics → one 45-minute task among 999 twenty-second tasks is classic skew.
  5. Shuffle read/write and spill. Heavy disk spill means partitions too large for execution memory.
  6. Compare shuffle bytes to input bytes. Shuffle much larger than input means something exploded rows — an explode, or duplicate keys on both sides of a join causing many-to-many expansion.
  7. GC time and executor memory. >20% GC means memory pressure, excessive caching, or too-wide rows.
  8. Only now consider more resources.

15 Twenty questions with model answers

QuestionAnswer
1. Partitions vs tasks?Within a stage, one task per partition. That task runs on one executor core.
2. Are partitions tied to executors?No. The scheduler can run a partition's task on any suitable free executor.
3. When does Spark create stages?When an action triggers execution, the physical plan is split into stages at shuffle boundaries.
4. Is filter a stage?No. Scan, filter, select and other narrow operations pipeline into one stage.
5. Why is groupBy wide?The same key exists in many partitions, so partial aggregates must be redistributed by key.
6. Does every executor get the whole 1 TB?No. Each executor reads only the byte ranges for its assigned tasks.
7. What happens after a shuffle?A new set of shuffle partitions exists; the next stage creates tasks that read them.
8. What is the Delta log?Table-level transaction metadata recording files added and removed, supporting versioned snapshots.
9. Is the Delta log per customer ID?No — it belongs to the whole table and is file-level, not row-level.
10. How does MERGE update an immutable file?It rewrites the affected files and commits add/remove actions so the new snapshot points at the replacements.
11. What does remove mean?Logically removed from the current snapshot. The file stays on disk until VACUUM — which is what enables time travel.
12. How does time travel work?Delta computes the active file set for the requested version/timestamp and reads those files.
13. Time travel vs SCD2?Time travel is system history (table snapshots, bounded by VACUUM). SCD2 is business history stored as rows.
14. Optimistic concurrency?Writers proceed optimistically, then validate at commit. Conflicting stale changes are detected and the write fails rather than silently losing data.
15. OPTIMIZE vs VACUUM?OPTIMIZE compacts file layout. VACUUM physically deletes unreferenced files after retention.
16. What causes skew?A few keys dominate, creating oversized shuffle partitions and straggler tasks.
17. Broadcast vs sort-merge?Broadcast ships a small side to all executors, avoiding a shuffle on the large side. Sort-merge shuffles and sorts both sides by key.
18. What is AQE?Runtime re-optimisation using real shuffle statistics: coalesce partitions, switch join strategy, split skewed partitions.
19. Job suddenly 6× slower?Compare inputs → find the slow stage → read the plan (did a broadcast stop happening?) → check skew/spill/GC → fix the root cause.
20. Explain Spark in one minute.See the memory sheet on the next page.
Whiteboard scenario — "design a production pipeline." Sources land in Bronze via Auto Loader with checkpoints and ingest metadata. Silver holds all conforming logic in one place — validation, dedup, type conformance — written with MERGE for idempotency. Gold holds business aggregates, small and rebuildable. Unity Catalog governs access and provides lineage. Workflows orchestrate with task dependencies and failure alerts. Every stage is idempotent so a re-run is safe. Maintenance runs OPTIMIZE and VACUUM on a schedule. Monitoring watches input volume, task skew, and job duration trends — not just success/failure.

16 One-page memory sheet

The twelve facts

1Driver plans and schedules; executors compute; cores are task slots.
2One task per partition, per stage. Partitions are not owned by executors.
3Input partitions come from scan planning — file sizes, splittability, config.
4Stages are cut only at shuffle boundaries. Narrow ops pipeline together.
5Wide = the dependency crosses partitions. Not "many columns".
6groupBy: partial aggregate locally → shuffle by key → final aggregate.
7Delta = Parquet + a folder of JSON commits. The log is table-level.
8MERGE rewrites whole files; remove is logical, which is why time travel works.
9OPTIMIZE compacts; ZORDER makes stats selective; VACUUM deletes and ends time travel.
10Skew: max/median task duration > 10×. More executors will not split one hot partition.
11Broadcast passes through the driver — it causes driver OOM too.
12Exactly-once needs a replayable source and an idempotent sink. Use batchId.
The closing sentence. "I separate compute from data layout. Executors provide task slots, partitions define units of work, stages are separated by shuffle boundaries, and Delta Lake makes cloud-file storage transactional, versioned, and reliable for production data engineering."
