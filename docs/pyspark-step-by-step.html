PySpark — Step by Step

A practical path from install to production patterns. One dataset, twelve lessons, every concept demonstrated rather than described.

How to useRun every command. The value is in reading the query plan after each change — not in reading this document.
DatasetNYC Yellow Taxi, January 2024. 48 MB Parquet, 2,964,624 rows, one free download, no signup.
Time~4 hours. Lessons 1–6 in one sitting, 7–12 in another.
PrereqPython and SQL basics. No Spark knowledge assumed.

The one habit. After every change, run df.explain("formatted") and diff the plan against the previous one. Not the timing — the plan. Timing tells you something changed; the plan tells you what and why. Count the Exchange nodes: each one is a shuffle, a stage boundary, and a place your job can die.

1 Setup

Install

brew install openjdk@17           # Spark runs on the JVM
pip install pyspark==3.5.1 pandas pyarrow

Verify:

python -c "import pyspark; print(pyspark.__version__)"
java -version

Your first SparkSession

from pyspark.sql import SparkSession, functions as F

spark = (SparkSession.builder
    .appName("taxi-lab")
    .master("local[4]")                              # 4 cores on this machine
    .config("spark.driver.memory", "4g")
    .config("spark.sql.shuffle.partitions", "8")     # default 200 is wrong for small data
    .getOrCreate())

spark.sparkContext.setLogLevel("WARN")               # Spark's INFO logging is a firehose
print(spark.version)
master("local[4]")Run driver and executor in one JVM with 4 task slots. Use local[*] for all cores. Omit entirely on a cluster.
shuffle.partitionsThe most important knob. Default is 200. For small data that means 200 tiny tasks and scheduling overhead dominates. Rule of thumb: 2–4× your core count for small data.
setLogLevel("WARN")Non-negotiable. Otherwise your output is buried.

The Spark UI — open it now

While a job is running, visit http://localhost:4040. This is where you will spend most of your debugging time. It dies when the SparkSession stops, so in a script add:

input("Press Enter to shut down...")     # keeps the UI alive
spark.stop()
Notebooks are fine for learning, but the UI is the real teacher. Every lesson below ends with something to look at there.

2 Loading data

Get the dataset

curl -O https://d37ci6vzurychx.cloudfront.net/trip-data/yellow_tripdata_2024-01.parquet

48 MB. Public domain, no signup.

Read it

taxi = spark.read.parquet("yellow_tripdata_2024-01.parquet")

taxi.printSchema()
print(taxi.count())
root |-- VendorID: integer |-- tpep_pickup_datetime: timestamp_ntz |-- tpep_dropoff_datetime: timestamp_ntz |-- passenger_count: long |-- trip_distance: double |-- PULocationID: integer |-- fare_amount: double ... 19 columns total 2964624
Both lines returned instantly. Why?
• The schema came from the Parquet footer — a few KB of metadata, not the data.
• count() was summed from row-group metadata, also without reading data.

Parquet is self-describing. This is the single biggest practical advantage over CSV.

CSV is different — and slower

# The lazy, wrong way
df = spark.read.option("header","true").option("inferSchema","true").csv("data.csv")   # SLOW
inferSchema=true must read the entire file to guess types. It launches a real Spark job before you have called any action. On a 10 GB CSV that is a full scan you did not ask for.
# The correct way — declare the schema
df = (spark.read
    .schema("id INT, name STRING, amount DOUBLE, ts TIMESTAMP")
    .option("header", "true")
    .option("mode", "FAILFAST")       # abort on bad rows instead of silently nulling them
    .csv("data.csv"))
ModeBehaviour on a malformed row
PERMISSIVE (default)Silently nulls the bad fields. How pipelines quietly lose data for months.
FAILFASTAbort immediately. Use in production.
DROPMALFORMEDDiscard bad rows without telling you.

Look at the data

taxi.show(5)                        # prints a text table
taxi.select("trip_distance", "fare_amount").describe().show()
taxi.limit(20).toPandas()           # limit FIRST, then collect
Never taxi.toPandas() or taxi.collect() on a full table. Both pull every row into the driver's memory. On 3M rows you will survive; on 300M you will not.

3 Lazy evaluation

This is the concept everything else depends on. Get it wrong and Spark's behaviour looks random.

Watch the clock

import time

t0 = time.time()
pipeline = (taxi
    .filter(F.col("trip_distance") > 0)
    .filter(F.col("fare_amount") > 0)
    .withColumn("hour", F.hour("tpep_pickup_datetime"))
    .select("hour", "trip_distance", "fare_amount"))
print(f"built in {time.time()-t0:.4f}s")

t0 = time.time()
print(pipeline.count())
print(f"executed in {time.time()-t0:.2f}s")
built in 0.0100s <-- four transformations, nothing computed 2955089 executed in 0.85s <-- the action did all the work
A DataFrame is a recipe, not a result. Each transformation returns a new DataFrame wrapping a new plan node. Nothing runs until an action demands a result. This lets Spark see your whole pipeline at once and optimise it before executing anything.

Transformations vs actions

Transformations (lazy)Actions (trigger execution)
select filter withColumn join groupBy orderBy drop distinct count() show() collect() take(n) write.* toPandas()

Actions ranked by danger

count(), show(n), take(n)Safe
write.parquet(...)Safe — the right way to materialise big results
collect(), toPandas()Driver OOM. Pulls everything to one machine.

Spark does not remember results

t0=time.time(); pipeline.count(); print(f"{time.time()-t0:.2f}s")
t0=time.time(); pipeline.count(); print(f"{time.time()-t0:.2f}s")   # SAME cost

Both calls re-read and re-process everything. There is no automatic caching. This is why Lesson 10 exists, and why sprinkling df.count() between pipeline steps for logging can triple your runtime.

In the UI: Jobs tab → you should see one job per action, each with the same duration.

4 Reading explain()

This is your EXPLAIN. Learn to read it and Spark stops being mysterious.

taxi.filter(F.col("fare_amount") > 100).select("fare_amount", "trip_distance") \
    .explain("formatted")
== Physical Plan == * Project (4) +- * Filter (3) +- * ColumnarToRow (2) +- Scan parquet (1) (1) Scan parquet Output [2]: [fare_amount#10, trip_distance#4] ReadSchema: struct<trip_distance:double,fare_amount:double> PushedFilters: [IsNotNull(fare_amount), GreaterThan(fare_amount,100.0)]

The four things to look for

Read bottom-upExecution starts at the leaves (the scan) and flows up.
The * prefixWhole-stage code generation — these operators were fused into one tight Java loop. Missing stars are a performance smell (usually a Python UDF).
PushedFiltersFilters handed to the file reader itself, which skips row groups using min/max statistics. Note Spark added IsNotNull for free.
ReadSchemaProof of column pruning — only 2 of 19 columns read.

What is absent matters most

No Exchange node means no shuffle, which means this is one stage. Scan any plan for Exchange and count them. Each is a network transfer and a stage boundary. That count is your cost estimate before you run anything.

What does not push down

taxi.filter(F.col("tpep_pickup_datetime") < F.col("tpep_dropoff_datetime")).explain("formatted")
PushedFilters: [] <-- EMPTY

Row-group statistics compare a column to a literal, never to another column. Column-to-column predicates and filters on derived columns always evaluate in Spark, after reading.

Plan vocabulary

Exchange hashpartitioningShuffle by key. Expensive.
Exchange SinglePartitionAlarm. Everything to one task.
BroadcastHashJoinThe good join — no shuffle on the big side
SortMergeJoinThe scalable join — 2 shuffles + 2 sorts
HashAggregate (×2)Good — partial then final, map-side combine happened
BatchEvalPythonA Python UDF. Codegen broken here.

5 Transformations

clean = (taxi
    .filter(F.col("trip_distance") > 0)
    .filter(F.col("fare_amount") > 0)
    .filter(F.col("passenger_count").between(1, 6))
    .withColumn("duration_min",
        (F.unix_timestamp("tpep_dropoff_datetime") -
         F.unix_timestamp("tpep_pickup_datetime")) / 60.0)
    .filter(F.col("duration_min").between(1, 240))
    .withColumn("mph", F.col("trip_distance") / (F.col("duration_min") / 60.0))
    .filter(F.col("mph") < 100)
    .withColumn("hour", F.hour("tpep_pickup_datetime"))
    .withColumn("dow",  F.date_format("tpep_pickup_datetime", "E"))
    .withColumn("tip_pct", F.round(100 * F.col("tip_amount") / F.col("fare_amount"), 1)))

print(f"kept {clean.count() / taxi.count():.1%}")
kept 95.2%
Always print the retention ratio. A filter that unexpectedly drops 40% of rows is a bug you want to find here, not in a dashboard three weeks later.

Nulls will silently eat your rows

taxi.filter(F.col("passenger_count").isNull()).count()

Roughly 5% of rows have a null passenger_count. The filter .between(1,6) drops every one of them, because in SQL NULL BETWEEN 1 AND 6 evaluates to NULL, not TRUE — and only TRUE passes a filter.

Three-valued logic is the #1 silent bug in Spark. A row with a null fails both cond and ~cond. So splitting data into "valid" and "invalid" branches this way loses rows from both. Always assert: 
assert valid.count() + invalid.count() == total.count()

Auditing nulls

taxi.select([
    F.sum(F.col(c).isNull().cast("int")).alias(c) for c in taxi.columns
]).show()

count(col) skips nulls, so you cannot count nulls with it. Convert the condition to 1/0 and sum. The list comprehension does all columns in one pass.

The withColumn-in-a-loop trap

# DON'T — one plan node per iteration. With 500 columns this hangs the DRIVER
# for minutes on ZERO rows of data.
for c in cols:
    df = df.withColumn(c, F.trim(F.col(c)))

# DO — one plan node
df = df.select(*[F.trim(F.col(c)).alias(c) for c in cols])

Catalyst's rule application is roughly quadratic in plan depth. This is a genuine production incident pattern.

6 Aggregations — your first shuffle

hourly = (clean
    .groupBy("hour")
    .agg(
        F.count("*").alias("trips"),
        F.round(F.avg("fare_amount"), 2).alias("avg_fare"),
        F.round(F.avg("mph"), 1).alias("avg_mph"),
        F.expr("percentile_approx(duration_min, 0.5)").alias("p50_min"),
        F.expr("percentile_approx(duration_min, 0.95)").alias("p95_min"))
    .orderBy("hour"))

hourly.show(24)
hour trips avg_fare avg_mph p50_min p95_min 0 41429 21.65 14.2 11.0 31.0 5 19827 23.10 22.8 9.0 26.0 <- fastest hour 17 178901 18.90 9.1 15.0 42.0 <- slowest hour
Use percentiles, not averages, for anything latency-shaped. p95 runs 2–3× p50 here. The mean tells you neither the typical case nor the bad case.

What physically happens

hourly.explain("formatted")
HashAggregate(keys=[hour], functions=[... FINAL ...]) +- Exchange hashpartitioning(hour, 8) <-- THE SHUFFLE +- HashAggregate(keys=[hour], ... PARTIAL) <-- map-side combine +- Scan parquet
  1. Partial aggregate — each input partition builds a local hash map. 3M rows collapse to at most 24 partial rows before anything crosses the network.
  2. Exchange — partial rows are sent to partition hash(hour) % 8. Each map task writes shuffle files to local disk.
  3. Final aggregate — merges the partials per key.
avg is decomposed into sum and count precisely because that decomposition is associative. That is what makes distributed averaging possible at all.

The expensive one: countDistinct

F.countDistinct("PULocationID")                       # slow
F.approx_count_distinct("PULocationID", 0.02)         # 10-100x faster, 2% error

Distinct counts are not mergeable — you cannot combine two partial distinct-counts without the underlying values. So Spark must shuffle raw pairs instead of compressed partials. approx_count_distinct uses a fixed-size HyperLogLog sketch, which is mergeable.

Conditional aggregation in one pass

clean.groupBy("dow").agg(
    F.count("*").alias("trips"),
    F.sum(F.when(F.col("tip_pct") > 20, 1).otherwise(0)).alias("big_tips"),
    F.round(F.avg(F.when(F.col("hour") < 6, F.col("fare_amount"))), 2).alias("night_fare")
).show()

In the UI: Stages tab → find the stage with non-zero "Shuffle Write" → open Summary Metrics. Compare median vs max task duration. That comparison is the most useful thing in the UI.

7 Joins

curl -O https://d37ci6vzurychx.cloudfront.net/misc/taxi_zone_lookup.csv
zones = (spark.read
    .option("header", "true")
    .schema("LocationID INT, Borough STRING, Zone STRING, service_zone STRING")
    .csv("taxi_zone_lookup.csv"))

print(zones.count())        # 265 rows — tiny, ideal broadcast candidate

pickup = (zones
    .withColumnRenamed("LocationID", "PULocationID")
    .withColumnRenamed("Zone", "pickup_zone")
    .withColumnRenamed("Borough", "pickup_borough")
    .select("PULocationID", "pickup_zone", "pickup_borough"))

enriched = clean.join(F.broadcast(pickup), "PULocationID", "left")
enriched.explain("formatted")
BroadcastHashJoin [PULocationID], [PULocationID], LeftOuter, BuildRight :- Scan parquet ... <-- NO Exchange on the big side! +- BroadcastExchange HashedRelationBroadcastMode

Join types

TypeReturns
innerOnly matching rows
leftAll left rows; nulls where no match
left_semiLeft rows that have a match. Left columns only. Never duplicates.
left_antiLeft rows with no match. The cleanest way to find orphans.
# find trips referencing an unknown zone
clean.join(pickup, "PULocationID", "left_anti").count()

The two strategies

StrategyHow it worksCost
BroadcastHashJoinSmall side copied to every executor; big side never moves Fast. Needs the small side to fit in memory.
SortMergeJoinBoth sides shuffled by key and sorted, then merged Scales to any size. 2 shuffles + 2 sorts.
# force sort-merge to compare
smj = clean.join(pickup.hint("merge"), "PULocationID", "left")
smj.explain("formatted")    # now shows TWO Exchange nodes
Broadcast passes through the DRIVER. Spark collects the small side to the driver, builds a hash table, then ships it out. A 2 GB broadcast needs 2 GB of driver heap plus 2 GB on every executor. Broadcasts cause driver OOM, not just executor OOM.

broadcast() is a hint, not a guarantee. Spark ignores it for FULL OUTER joins. Always verify BroadcastHashJoin in the plan.

The many-to-many explosion

The #1 cause of a "should be fast" join running for hours. Duplicate keys on both sides multiply rows: 1000 × 1000 matching rows for one key produces 1,000,000 output rows from 2,000 inputs.

Check before joining: 
for name, d in [("left", clean), ("right", pickup)]:
    n = d.groupBy("PULocationID").count().filter("count > 1").count()
    print(name, "duplicate keys:", n)

8 Window functions

Anything of the form "compare this row to others in its group" is a window.

from pyspark.sql.window import Window

w = Window.partitionBy("pickup_borough").orderBy(F.desc("trips"))

zone_rank = (enriched
    .groupBy("pickup_borough", "pickup_zone")
    .agg(F.count("*").alias("trips"),
         F.round(F.avg("fare_amount"), 2).alias("avg_fare"))
    .withColumn("rank", F.row_number().over(w))
    .withColumn("borough_total", F.sum("trips").over(Window.partitionBy("pickup_borough")))
    .withColumn("pct", F.round(100 * F.col("trips") / F.col("borough_total"), 1))
    .filter(F.col("rank") <= 5)
    .orderBy("pickup_borough", "rank"))

zone_rank.show(30)
pct compares each row to its group's aggregate with no self-join. That is the main reason window functions exist.

A window is a shuffle in disguise

Window [...] +- Sort [pickup_borough, trips DESC] +- Exchange hashpartitioning(pickup_borough, 8) <-- shuffle + sort

Nothing in the syntax hints at this. Both window specs above partition by the same column, so Spark reuses one Exchange. Reusing the partitioning key across specs is a real and underused optimisation.

rank vs row_number vs dense_rank

amounts:  500, 300, 300, 100
row_number:  1, 2, 3, 4      strictly sequential, ties broken arbitrarily
rank:        1, 2, 2, 4      ties share, gaps appear
dense_rank:  1, 2, 2, 3      ties share, no gaps
filter(row_number <= 3) gives exactly 3 rows. filter(rank <= 3) can give 50 if there are ties. "Top N per group" almost always means row_number. Choosing wrong is a silent correctness bug — nothing errors.

Running totals and lag

w_time = Window.partitionBy("PULocationID").orderBy("tpep_pickup_datetime")

(clean
 .withColumn("running_fares", F.sum("fare_amount").over(w_time))
 .withColumn("prev_fare",     F.lag("fare_amount", 1).over(w_time))
 .withColumn("delta",         F.col("fare_amount") - F.lag("fare_amount", 1, 0.0).over(w_time))
 .withColumn("ma_10",         F.avg("fare_amount").over(w_time.rowsBetween(-9, 0))))
Default frame with orderByunboundedPreceding → currentRow — a running total
Default frame with no orderByThe entire partition — a group total

Same function, completely different answer. Most "my window result is wrong" bugs are this default.

Never omit partitionBy. 
Window.orderBy("ts")     # NO partitionBy — all rows to ONE partition
The plan shows Exchange SinglePartition: one task, one core, the whole dataset. Spark even logs a warning about it.

9 Partitions and skew

A partition is a chunk of data processed by one task. Partition count = parallelism.

See the distribution

(clean
 .withColumn("pid", F.spark_partition_id())
 .groupBy("pid").count().orderBy("pid").show())

spark_partition_id() exposes the physical partition index as a column. The best diagnostic function in Spark — it turns an invisible property into a queryable table.

repartition vs coalesce

repartition(n)coalesce(n)
ShuffleYes, fullNo
Can increase countYesNo (silently ignored)
Even distributionYesNo
Use forFixing skew, preparing a joinReducing output files at the very end
The coalesce(1) trap. 
big_df.coalesce(1).write.parquet(path)      # DANGEROUS
big_df.repartition(1).write.parquet(path)   # safe
Because coalesce does not shuffle, it propagates upstream and reduces the parallelism of the entire preceding stage to 1. Your 100-core aggregation now runs single-threaded. repartition(1) inserts an Exchange, creating a stage boundary, so upstream work keeps its parallelism.

Skew — measure it

(clean.groupBy("PULocationID").count()
      .agg(F.min("count").alias("min"),
           F.expr("percentile_approx(count, 0.5)").alias("p50"),
           F.max("count").alias("max"))
      .show())

Read the max / p50 ratio. Above ~10× means one task does an order of magnitude more work than the median, and a stage cannot finish until its slowest task does.

Real keys follow a Zipf distribution. Users, merchants, device ids, product SKUs routinely show 1000×+ ratios. Anyone who has run Spark in production has been paged because of this.

Fixing skew

1. Let AQE handle it (Spark 3+, on by default). It splits oversized shuffle partitions after seeing real sizes, and replicates the matching side.

spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")

Limitation: helps joins only. Not skewed groupBy, not windows.

2. Salting — the manual technique.

SALT = 16
big   = df.withColumn("salt", (F.rand(seed=42) * SALT).cast("int")) \
          .withColumn("skey", F.concat_ws("_", "key", "salt"))

# the small side must be REPLICATED, once per salt value
small = dim.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(SALT)]))) \
           .withColumn("skey", F.concat_ws("_", "key", "salt"))

result = big.join(small, "skey").groupBy("key").agg(...)   # aggregate back on the REAL key
The small side must be replicated, not salted randomly. If you salted both sides randomly, a big-side row with salt 7 would never meet its partner at salt 3 and you would silently lose rows. This is the step people get wrong in interviews.

Also: seed the rand(). Unseeded makes the job non-deterministic, so a retried task assigns different salts than its first attempt.

10 Caching

from pyspark import StorageLevel

base = clean.select("hour", "PULocationID", "fare_amount", "mph")

# WITHOUT cache — three actions, three full recomputes
t0 = time.time()
base.count()
base.select("PULocationID").distinct().count()
base.groupBy("hour").count().count()
t_nocache = time.time() - t0

# WITH cache
base.persist(StorageLevel.MEMORY_AND_DISK)
base.count()                 # materialise — this call pays the cost
t0 = time.time()
base.count()
base.select("PULocationID").distinct().count()
base.groupBy("hour").count().count()
t_cache = time.time() - t0
base.unpersist()

print(f"no cache {t_nocache:.1f}s   cached {t_cache:.1f}s")
no cache 4.2s cached 1.1s (roughly 4x on this dataset)

The rules

persist() is lazyIt only registers intent. Call an action to actually cache. Forgetting this makes your benchmark meaningless.
MEMORY_AND_DISKThe right default. Blocks that don't fit spill to disk rather than being dropped. cache() is an alias for this on DataFrames.
unpersist()Always. In a long-running app, forgotten caches occupy storage memory forever and starve execution memory.

When caching makes things slower

• Used once. You pay materialisation and memory for zero reuse. Cache only what is read 2+ times.
• Cache evicts cache. Storage and execution share one memory region. A big cache causes shuffle spill in other stages — you made stage 3 faster and stage 7 slower.
• Caching blocks pushdown. Caching before filtering materialises everything and prevents filters reaching the scan. Cache the narrow, filtered DataFrame, not the raw source.

In the UI: Storage tab → shows what is actually cached and how much fits in memory. A DataFrame showing "40% cached" is giving you almost no benefit while consuming memory.

11 Writing data

(enriched
    .withColumn("pickup_date", F.to_date("tpep_pickup_datetime"))
    .repartition("pickup_date")            # <-- pair with partitionBy
    .write
    .mode("overwrite")
    .partitionBy("pickup_date")
    .option("compression", "snappy")
    .parquet("output/trips"))
The most important line here is repartition("pickup_date") before partitionBy("pickup_date").

Without it, every task can hold rows for every date, so each task writes one small file per date: n_tasks × n_dates files. With 200 tasks and 30 dates that is 6,000 tiny files. With it, each task holds one date.

Why small files hurt — four separate costs

1. ListingThe driver enumerates every file. On S3 this is paginated API calls and can take minutes with the cluster idle.
2. TasksOne task per file — thousands each doing microseconds of real work.
3. MetadataEvery Parquet file has a footer. With tiny files the footer can exceed the data.
4. CompressionDictionary and RLE encodings need volume to be effective.

Target 128 MB – 1 GB per file.

Verify partition pruning works

out = spark.read.parquet("output/trips")
out.filter(F.col("pickup_date") == "2024-01-15").explain("formatted")
PartitionFilters: [isnotnull(pickup_date), (pickup_date = 2024-01-15)]

Whole directories are skipped — those files are never opened. Cost order:
partition pruning (directory level, free) > row-group pushdown (file level, cheap) > full scan then filter (expensive).

Write modes

overwriteReplaces. On a partitioned table this deletes EVERY partition unless you set spark.sql.sources.partitionOverwriteMode=dynamic.
appendAdds files, keeps existing
errorFails if path exists (default)
Static overwrite mode + a one-day incremental load = you just deleted five years of history. Set dynamic for any incremental pipeline.

12 Production

The Spark UI — what to click, in order

JobsWhich job is slow. One job per action. More jobs than actions means something extra ran (schema inference, a broadcast collect).
StagesOpen the slow stage → Summary Metrics. Compare median vs max for Duration, Shuffle Read, and Spill.
SQL / DataFrameThe most valuable tab. The plan as a DAG with per-operator row counts and timings.
StorageWhat is actually cached and how much fits.
ExecutorsGC time, failed tasks, shuffle I/O per executor.

Metrics and their thresholds

MetricHealthyInvestigate when
Task max / median duration< 3×> 10× → skew
Shuffle read per task50–200 MB> 1 GB: raise partitions. < 5 MB: lower them.
Spill (disk)0> 0 and large → partitions too big
GC time< 10% of task time> 20% → memory pressure
Task count per stage2–4× cores> 10×: overhead. < 1×: idle cores.

The tuning order — follow it

1Reduce dataFilter early, select only needed columns, exploit partition pruning
2Fix the planBroadcast small dimensions, avoid gratuitous repartitions
3Fix skewAQE, then salting
4Size partitionsshuffle.partitions for ~128 MB per task
5Then add memory or executorsOnly after all of the above

Reversing this order is what a weak engineer does. Most "we need a bigger cluster" problems are step 1 or 3.

UDFs — the cost hierarchy

1. Built-in functions       1x        stays in JVM codegen — 400+ of them exist
2. Pandas UDF (Arrow)      2-4x      vectorised batches
3. Python UDF             10-50x     per-row pickling + socket IPC
# if you must use one, FILTER FIRST — Catalyst will not push a filter through a UDF
df.filter("length(text) > 20").withColumn("score", my_udf("text"))

SymptomLikely causeFix

Executor OOMSkewed partition, oversized broadcastFix skew first, memory last
Slow, cluster idleDriver work: file listing, schema inferenceExplicit schemas, compact files

The traps, collected

1Explicit schemas. inferSchema is a full scan.
2Three-valued logic: a null row fails both cond and ~cond.
3count(col) skips nulls; count("*") does not.
4Never withColumn in a loop — use one select.
5Column-to-column and derived-column filters never push down.
6Broadcast passes through the driver — it causes driver OOM too.
7Duplicate keys on both sides of a join multiply rows.
8row_number not rank for "top N per group".
9A window with no partitionBy = one task for everything.
10coalesce(1) propagates upstream. Use repartition(1).
11repartition(col) before partitionBy(col). Always.
12Cache only what is read 2+ times, and unpersist() after.
