1 Install and connect

curl https://clickhouse.com/ | sh      # downloads a single binary
./clickhouse server                    # terminal 1 — leave running
./clickhouse client                    # terminal 2

One binary, no dependencies, no config file needed. The server listens on 9000 (native protocol) and 8123 (HTTP).

Credentials

Default user is default with no password. Nothing is generated for you to find.

./clickhouse client                              # just works
./clickhouse client --user default --password ''  # same thing
curl 'http://localhost:8123/?query=SELECT%20version()'
Where is my data? The server starts with --path=./, meaning the data directory is whatever folder you launched it from. Start it somewhere else and you get a fresh empty server while the old data sits in the previous folder. This confuses everyone once.

Set a password (optional for local dev)

ALTER USER default IDENTIFIED WITH sha256_password BY 'yourpassword';

Not needed locally — the listener binds to 127.0.0.1 only, so nothing off your machine can reach it. It matters the moment you bind to 0.0.0.0.

Useful client flags

-q "SQL"run one query and exit
--timeprint elapsed seconds — you'll use this constantly
--format PrettyCompactreadable tables
--multilinelet queries span lines in the shell

2 Load real data

Toy data teaches nothing about performance. Use the OpenCelliD dataset — 43 million real cell towers, publicly hosted, no signup.

Create the table

CREATE TABLE cell_towers
(
    radio    Enum8('' = 0, 'CDMA' = 1, 'GSM' = 2, 'LTE' = 3, 'NR' = 4, 'UMTS' = 5),
    mcc      UInt16,          -- country code
    net      UInt16,          -- operator
    area     UInt16,
    cell     UInt64,
    unit     Int16,
    lon      Float64,
    lat      Float64,
    range    UInt32,
    samples  UInt32,
    changeable UInt8,
    created  DateTime,
    updated  DateTime,
    averageSignal UInt8
)
ENGINE = MergeTree
ORDER BY (radio, mcc, net, created);

Load it — no download step needed

INSERT INTO cell_towers
SELECT * FROM url('https://datasets.clickhouse.com/cell_towers.csv.xz', 'CSVWithNames',
'radio String, mcc UInt16, net UInt16, area UInt16, cell UInt64, unit Int16,
 lon Float64, lat Float64, range UInt32, samples UInt32, changeable UInt8,
 created DateTime, updated DateTime, averageSignal UInt8');
43,276,150 rows in 33 seconds (~1.3 million rows/sec)

url() streams the download, decompresses the .xz, and parses the CSV in one statement. Nothing touches local disk. The same works for s3(), file(), and https Parquet.

First look

SELECT radio, count() AS towers FROM cell_towers GROUP BY radio ORDER BY towers DESC;
UMTS 20,686,487 47.8% LTE 12,101,148 28.0% GSM 9,931,304 22.9% CDMA 556,344 1.3% NR 867 0.0% <- snapshot is from Feb 2021, 5G barely deployed Query time: 0.033 sec
33 milliseconds to aggregate 43 million rows on a laptop. That is the whole pitch. No cluster, no tuning, no indexes created. Keep this number in mind for the rest of the guide.

3 ORDER BY is everything

If you learn one thing from this guide, learn this. ORDER BY in a MergeTree table is not a sorting preference. It is:

  1. The physical order rows are stored on disk
  2. The primary index ClickHouse uses to skip data

How the sparse index works

Rows are stored sorted by ORDER BY, split into GRANULES of 8192 rows.
ClickHouse stores ONE index entry per granule — not per row.

granule 0  -> first row: (LTE, 202, ...)
granule 1  -> first row: (LTE, 208, ...)
granule 2  -> first row: (LTE, 310, ...)   <- binary search lands here
...
5284 granules total for 43M rows

WHERE radio='LTE' AND mcc=310
  -> binary search the index
  -> read ONLY the matching granules
Sparse, not dense. A B-tree index in Postgres points at individual rows. ClickHouse points at blocks of 8192. That is why the index is tiny enough to sit in memory for a 43M-row table, and why ClickHouse is not good at single-row lookups — it always reads at least one full granule.

Choosing the columns

RuleWhy
Put the column you filter on most firstOnly a leading prefix can be binary-searched
Low cardinality first, high lastBetter compression, better skipping
Time column usually lastNaturally sorted within each group
3–4 columns is plentyLater columns rarely help
-- Multi-tenant serving: tenant id FIRST, always
ORDER BY (company_id, event_date, device_id)

-- Not this — company_id filters can't use the index
ORDER BY (event_date, device_id, company_id)
You cannot change ORDER BY later. Only extend it with more columns at the end. Changing the existing columns means creating a new table and copying everything. Choose deliberately on day one.

4 Reading EXPLAIN

This is how you verify the index is doing work. Run it on every slow query.

A query that uses the index

EXPLAIN indexes = 1
SELECT count() FROM cell_towers WHERE radio = 'LTE' AND mcc = 310;
Indexes: PrimaryKey Keys: radio, mcc Condition: and((mcc in [310, 310]), (radio in [3, 3])) Parts: 4/4 Granules: 330/5284 <-- 93.8% SKIPPED Search Algorithm: binary search

A query that does not

EXPLAIN indexes = 1
SELECT count() FROM cell_towers WHERE lat BETWEEN 51.0 AND 51.9;
Indexes: PrimaryKey Condition: true <-- no usable condition Parts: 4/4 Granules: 5284/5284 <-- FULL SCAN, 0% skipped
The two lines that matter:
Granules: 330/5284 — how much data was skipped. This is your index effectiveness.
Condition: true — means the index could say nothing. Your filter column is not in ORDER BY.

Other EXPLAIN modes

EXPLAIN indexes=1granule skipping — use this one
EXPLAIN PIPELINEthe parallel execution stages
EXPLAIN ESTIMATErows/parts it expects to read
EXPLAIN SYNTAXthe query after rewriting

Bonus: why count() is instant

SELECT count() FROM cell_towers;   -- 0.001 sec

A bare count() is answered from part metadata. No data is read at all.

5 Table engines

The engine decides how data is stored and what happens on merge. 95% of tables are one of the first two.

EngineBehaviourUse for
MergeTreePlain append-onlyFacts, events, logs
ReplacingMergeTree(ver)Keeps last row per keyUpserts, dimensions, CDC
SummingMergeTreeSums numeric columns per keyRollup targets
AggregatingMergeTreeMerges aggregate statesuniq / avg / quantile rollups
Replicated*Any of the above + replicationProduction HA

ReplacingMergeTree — the upsert pattern

CREATE TABLE devices (
    device_id String,
    status    String,
    updated   DateTime
) ENGINE = ReplacingMergeTree(updated)
ORDER BY device_id;                    -- ORDER BY == the dedup key

INSERT INTO devices VALUES ('d1', 'active',  now());
INSERT INTO devices VALUES ('d1', 'retired', now());   -- the "update"
Deduplication is eventual, not immediate. It happens during background merges at an unpredictable time. Until then you see both rows. 
SELECT * FROM devices;         -- may show BOTH rows
SELECT * FROM devices FINAL;   -- correct now, slightly slower
FINAL is the single biggest surprise for anyone coming from Postgres or MySQL.

What is a "part"?

data/default/cell_towers/
├── all_1_31_2/     <- a PART: an immutable folder of sorted, compressed columns
├── all_32_37_1/
└── all_38_38_0/

Every INSERT writes new parts. Background threads merge small parts into bigger ones. That merging is where ReplacingMergeTree dedups and SummingMergeTree sums.

6 Inserting properly

The rule

Insert in big batches. 10,000 to 1,000,000 rows at a time.
Every INSERT statement creates at least one new part. Thousands of tiny inserts create thousands of parts, background merges can't keep up, and you hit TOO_MANY_PARTS and the table stops accepting writes.
-- BAD: 1000 statements = 1000 parts
INSERT INTO t VALUES (1);
INSERT INTO t VALUES (2);   ...

-- GOOD: one statement, many rows
INSERT INTO t VALUES (1),(2),(3), ... (100000);

When you can't batch — async inserts

SET async_insert = 1, wait_for_async_insert = 1;

ClickHouse buffers incoming rows server-side and flushes one part per ~10 MB or per second. This is the standard fix for high-frequency writes from an application or a Kafka consumer.

Loading from files

-- from the shell
clickhouse client -q "INSERT INTO t FORMAT Parquet"      < data.parquet
clickhouse client -q "INSERT INTO t FORMAT CSVWithNames" < data.csv

-- from SQL
INSERT INTO t SELECT * FROM file('/path/data.parquet', Parquet);
INSERT INTO t SELECT * FROM url('https://host/data.csv', CSVWithNames);
INSERT INTO t SELECT * FROM s3('https://bucket/*.parquet', 'key', 'secret', 'Parquet');

ClickHouse batches internally too

The 43M-row load in Lesson 2 was a single statement, but it produced 39 parts — ClickHouse split the stream at max_insert_block_size (about 1 million rows), sorted and wrote each block, then merged them down to 4 in the background. Memory stayed flat the whole time.

7 Updates and deletes

This is where ClickHouse is least like a normal database. Parts are immutable — once written, never edited. So an UPDATE cannot change rows in place.

What actually happens

ALTER TABLE t UPDATE salary = salary * 1.1 WHERE dept = 'eng';
        |
        v
  queued as a MUTATION (a text file on disk)
        |
        v
  background: read part -> apply change -> write NEW part -> drop old

The statement returns immediately. The work happens later. Updating one row can rewrite gigabytes.

Mutations are async, have no rollback, and no transaction. Your next SELECT may still show old values. Force it to wait: 
ALTER TABLE t UPDATE x = 1 WHERE y = 2 SETTINGS mutations_sync = 1;

Deletes — use the lightweight one

DELETE FROM t WHERE id = 1;              -- lightweight, cheap, use this
ALTER TABLE t DELETE WHERE id = 1;       -- heavyweight mutation, avoid

Lightweight delete just flags rows in a hidden _row_exists column. Physical removal waits for a merge.

Clearing a column

ALTER TABLE t CLEAR COLUMN email;                        -- values -> default, rows KEPT
ALTER TABLE t CLEAR COLUMN email IN PARTITION '202301';  -- one partition only

Useful for GDPR erasure while keeping the schema. The IN PARTITION form limits the rewrite — on a big table that is the difference between seconds and hours.

The idiomatic alternative: don't update

CREATE TABLE state (id String, status String, ver DateTime)
ENGINE = ReplacingMergeTree(ver) ORDER BY id;

INSERT INTO state VALUES ('d1', 'active',  now());
INSERT INTO state VALUES ('d1', 'retired', now());   -- "update" = an append

SELECT * FROM state FINAL;   -- returns only the latest
Appends are cheap. Mutations are not. Use mutations for occasional backfills and GDPR deletes — never as your routine update path.

Monitoring mutations

SELECT command, is_done, parts_to_do, latest_fail_reason
FROM system.mutations WHERE NOT is_done;

KILL MUTATION WHERE mutation_id = '...';    -- no rollback: leaves it half-applied

8 Materialized views

A ClickHouse materialized view is an INSERT TRIGGER, not a cached query.
It fires on rows inserted after it is created. It never sees existing data and never re-reads the source table. That is why it is cheap.

The production pattern — three steps

-- 1. target table holds the data
CREATE TABLE towers_by_mcc (
    mcc UInt16, radio Enum8(...), yr UInt16,
    towers UInt64, range_sum UInt64
) ENGINE = SummingMergeTree ORDER BY (mcc, radio, yr);

-- 2. the MV is just the trigger
CREATE MATERIALIZED VIEW mv_by_mcc TO towers_by_mcc AS
SELECT mcc, radio, toYear(created) AS yr, count() AS towers, sum(range) AS range_sum
FROM cell_towers GROUP BY mcc, radio, yr;

-- 3. backfill existing rows manually
INSERT INTO towers_by_mcc
SELECT mcc, radio, toYear(created), count(), sum(range)
FROM cell_towers GROUP BY mcc, radio, toYear(created);

Measured result

Base tableRollup via MVGain
Rows43,276,1505,9077,300× fewer
Size896 MiB54 KiB17,000× smaller
Query time0.045 s0.002 s22× faster

Rules

Always use TO target_tableLets you drop and recreate the MV without losing data
Backfill manuallyPOPULATE misses rows inserted while it runs
SummingMergeTree for sums/countsMerges duplicate keys automatically
AggregatingMergeTree for uniq/avg/quantileThose are not summable

Non-summable aggregates

-- write with -State
CREATE MATERIALIZED VIEW mv TO agg AS
SELECT day, uniqState(user_id) AS users, avgState(price) AS avg_price
FROM events GROUP BY day;

-- read with -Merge
SELECT day, uniqMerge(users), avgMerge(avg_price) FROM agg GROUP BY day;

Mixing up -State and -Merge returns binary garbage, not an error.

MVs chain

Kafka table  ->  MV (parse JSON)  ->  events  ->  MV  ->  hourly  ->  MV  ->  daily

Raw data lands once; every rollup is maintained automatically on insert. This replaces scheduled refresh jobs entirely.

9 Compression

ClickHouse compresses per column. Default is LZ4 — fast, moderate ratio. You can pick a specialised codec per column.

The codecs worth knowing

CodecFor
T64Integers that don't use their full range. Strips unused high bits.
Delta, DoubleDeltaSorted timestamps, counters, monotonic values
GorillaFloats that change slowly (sensor readings)
ZSTD(1..22)General purpose. Apply after a specialised codec.
LowCardinality(String)Not a codec — a type. Use under ~10k distinct values.

Measured on the 43M-row table

samples UInt32   CODEC(T64, ZSTD(1))          77.2 MiB -> 21.7 MiB    71.9% saved
cell    UInt64   CODEC(T64, ZSTD(1))         178.7 MiB -> 108.2 MiB   39.5%
created DateTime CODEC(DoubleDelta, ZSTD(1))  87.9 MiB -> 54.3 MiB    38.2%
lat     Float64  CODEC(Gorilla, ZSTD(1))     260.1 MiB -> 247.9 MiB    4.7%
updated DateTime CODEC(DoubleDelta, ZSTD(1)) 131.1 MiB -> 135.7 MiB   -3.5%  <- WORSE

Table total: 1.07 GiB -> 896 MiB   (ratio 1.81 -> 2.22)
Why updated got worse. created is in ORDER BY, so it is stored sorted — consecutive deltas are tiny. updated is not sorted, so consecutive values jump randomly and the deltas are larger than the raw values.

Rule: Delta / DoubleDelta / Gorilla only pay off on columns correlated with the sort order. T64 works regardless, which is why it won everywhere.

Check your own table

SELECT name,
       formatReadableSize(sum(data_compressed_bytes))   AS compressed,
       formatReadableSize(sum(data_uncompressed_bytes)) AS uncompressed,
       round(sum(data_uncompressed_bytes) / sum(data_compressed_bytes), 2) AS ratio
FROM system.columns WHERE table = 'cell_towers'
GROUP BY name ORDER BY sum(data_compressed_bytes) DESC;

Start with the biggest column. That is where the win is.

10 Skip indexes and projections

Both solve the same problem: you need to filter on a column that is not in ORDER BY.

Skip index — cheap, partial help

ALTER TABLE cell_towers ADD INDEX idx_lat lat TYPE minmax GRANULARITY 4;
ALTER TABLE cell_towers MATERIALIZE INDEX idx_lat;   -- required for existing data
Skip Name: idx_lat Description: minmax GRANULARITY 4 Granules: 1948/5283 <-- 63% skipped
TypeFor
minmaxRange filters (BETWEEN, >, <)
set(N)Equality on low-cardinality columns
bloom_filter(p)Equality on high-cardinality columns
tokenbf_v1Text search inside strings
Skip indexes only skip — they never point at rows. On randomly distributed data they do nothing, because every block's min/max spans the whole range. They worked here because geography clusters naturally.

Projection — a second copy, differently sorted

ALTER TABLE cell_towers ADD PROJECTION proj_geo (SELECT * ORDER BY lat, lon);
ALTER TABLE cell_towers MATERIALIZE PROJECTION proj_geo;

Now the same query silently reads the projection instead:

ReadFromMergeTree (proj_geo) Granules: 222/5284 <-- 96% skipped

Measured — same query, three ways

StrategyGranules readTimeSpeedup
Baseline (nothing)5284 / 52840.206 s1×
Skip index (minmax)1948 / 52830.033 s6×
Projection222 / 52840.015 s14×

Aggregating projection — the biggest win

ALTER TABLE cell_towers ADD PROJECTION proj_mcc
  (SELECT mcc, radio, count(), avg(range) GROUP BY mcc, radio);
GROUP BY mcc, radio base table: 0.063 s projection: 0.002 s 31x faster
Which to use. Skip index is nearly free but only helps clustered data. A projection is a full second copy of the table (1.12 GiB here) but gives far better skipping. Aggregating projections are the best deal: a few MB for a 31× win.

11 SQL you won't find elsewhere

Top-N per group, no window function

SELECT * FROM events ORDER BY score DESC LIMIT 3 BY user_id;

Cheaper and shorter than row_number() OVER (PARTITION BY ...).

The -If combinator

SELECT countIf(status = 'error')      AS errors,
       avgIf(latency, status = 'ok')  AS ok_latency,
       sumIf(amount, country = 'US')  AS us_revenue
FROM events;

All computed in one pass. Replaces SUM(CASE WHEN ... END).

argMax / argMin

SELECT argMax(product_name, revenue) FROM sales;   -- the name from the highest-revenue row

Replaces a self-join or a window function.

Approximate aggregates

SELECT uniq(user_id),                     -- HyperLogLog, ~0.5% error, very fast
       uniqExact(user_id),                -- exact, slower
       quantile(0.95)(latency),           -- approximate percentile
       quantiles(0.5, 0.9, 0.99)(latency) -- several in one pass
FROM events;

Time bucketing

toStartOfHour(ts)          toStartOfDay(ts)         toStartOfMonth(ts)
toStartOfInterval(ts, INTERVAL 5 MINUTE)
toYear(ts)  toMonth(ts)  toDayOfWeek(ts)  toHour(ts)

Arrays

SELECT arrayJoin([1,2,3]);                       -- explode into rows
SELECT groupArray(user_id) FROM events;          -- collect into an array
SELECT arrayMap(x -> x * 2, [1,2,3]);            -- [2,4,6]
SELECT arrayFilter(x -> x > 1, [1,2,3]);         -- [2,3]

Gap filling

SELECT toStartOfDay(ts) AS day, count()
FROM events GROUP BY day ORDER BY day
WITH FILL FROM toDate('2026-01-01') TO toDate('2026-02-01') STEP INTERVAL 1 DAY;

Inserts rows for days with no data — no calendar table needed.

Case sensitivity

Keywords (SeLeCt)case-insensitive
Column / table / database namescase-sensitive
Function names (toYear)case-sensitive, camelCase
Aggregate names (count, SUM)case-insensitive (SQL standard)

12 Scaling and production

Scale vertically first

Unlike Spark, ClickHouse is single-node by default and that is usually enough. There is no shuffle — a GROUP BY streams blocks through vectorised operators and merges hash tables locally. Most production deployments never shard.

< 1 TB: single node. 1–10 TB: still single node. 10 TB+: consider sharding.

The scaling ladder — in order

1Fix ORDER BYFree. Usually the entire problem.
2Codecs, MVs, projections10–30×, no new hardware
3Bigger machineScales near-linearly with cores
4Add replicasFixes concurrency — usually the real bottleneck
5Tier cold data to S3Often defers sharding indefinitely
6ShardLast resort. Hard to undo.

Replicas vs shards — different problems

REPLICAS  -> same data, N copies   -> more concurrent READS + high availability
SHARDS    -> different data, split -> more DATA than one node can hold

If 500 dashboard users are slow, you need replicas. If 40 TB won't fit, you need shards.

Tiering to S3 — the step most people skip

ALTER TABLE events MODIFY TTL event_date + INTERVAL 90 DAY TO VOLUME 's3';

Hot 90 days on NVMe, history on S3, one table, no sharding. For most workloads this replaces sharding entirely.

Concurrency tuning

SET max_threads = 4,               -- one query won't eat all cores
    max_execution_time = 10,
    max_memory_usage = 10000000000;

By default one query uses every core. For dashboards, cap it — you trade single-query latency for concurrent throughput. This is the setting that makes hundreds of users work.

Monitoring — the queries to keep

-- storage per table
SELECT table, formatReadableSize(sum(data_compressed_bytes)) AS size,
       sum(rows) AS rows, count() AS parts
FROM system.parts WHERE active GROUP BY table ORDER BY sum(bytes_on_disk) DESC;

-- stuck mutations
SELECT command, parts_to_do, latest_fail_reason
FROM system.mutations WHERE NOT is_done;

-- in-flight merges
SELECT table, elapsed, progress FROM system.merges;

The 10 traps, collected

1ORDER BY is the index. It decides everything, and can't be changed later.
2ReplacingMergeTree dedup is eventual — you need FINAL.
3UPDATE/DELETE are async mutations that rewrite parts. No rollback.
4Small inserts create parts. Batch, or use async_insert.
5A materialized view never sees existing data. Backfill manually.
6Over-partitioning is worse than none. Monthly or daily only.
7SELECT from a Kafka engine table consumes the messages.
8Joins are weak. Use dictionaries or denormalise.
9Delta/Gorilla codecs backfire on unsorted columns.
10No transactions, no foreign keys, no constraints. It is OLAP.
