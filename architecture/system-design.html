Real-Time Analytics Platform

End-to-end system design. Device telemetry → customer-facing analytics. Kafka · Flink · S3 Tables (Iceberg) · ClickHouse — replacing Redshift.

ProblemIngest ~7B device events/day, derive trips and safety events, serve multi-tenant customer dashboards at sub-second latency.
TodayKafka → Flink → S3/Iceberg → Glue → Redshift Spectrum → materialized views → GraphQL
TargetSame pipeline, ClickHouse replaces Redshift for serving. S3 Tables remains the system of record.
Key decisionQuery Iceberg in place from ClickHouse (Option A), or materialise into MergeTree (Option B). Section 9 resolves it.

The one architectural principle. Flink owns all business logic. ClickHouse only reshapes for serving. If both systems independently derive a metric, the definitions will drift — not immediately, but the first time someone changes one and forgets the other. A customer finds it before your tests do.

1 Requirements & scope

Functional

F1Ingest device telemetry — GPS, speed, accelerometer, diagnostics — from a fleet of connected vehicles
F2Derive trips (start/end, distance, duration, route) from raw point events
F3Derive safety events — harsh braking, speeding, cornering — with severity scoring
F4Enrich with vehicle, driver and company metadata
F5Serve per-tenant dashboards: fleet summary, driver scorecards, trip history, safety trends
F6Support ad-hoc analytical queries by internal analysts
F7Retain raw events for replay and audit

Non-functional — the numbers that drive the design

RequirementTargetWhy it matters
Dashboard latencyp99 < 500 msCustomer-facing. This single number rules out querying object storage per request.
Concurrency200 concurrent queries peak5,000 tenants, business-hours skew
Data freshnessRefined ≤ 3 min · serving ≤ 10 minMust be published, not implied
Ingest throughput250K events/sec peak3× average
Availability99.9% serving~43 min/month budget
RetentionRaw 13 months · refined 7 yearsRegulatory and contractual
CorrectnessExactly-once to the lakeDuplicated safety events are a customer-visible defect

Explicitly out of scope

  • Real-time alerting on individual events (sub-second) — a separate path off Kafka, not this pipeline
  • ML model training — reads the same lake, different consumer
  • Device firmware, connectivity, and the ingest edge itself
The requirement that decides the architecture: p99 < 500 ms at 200 concurrent. Every subsequent choice — MergeTree over in-place Iceberg queries, the ORDER BY key, the materialized views — descends from this one line.

2 Capacity estimation

Ingest volume

Active devices                          200,000
Emission rate                           1 event / second while active
Active hours per device per day         10

Events per day    = 200,000 × 10 × 3,600           = 7.2 billion
Average rate      = 7.2e9 / 86,400                 = 83,000 events/sec
Peak rate (3×)                                     = 250,000 events/sec

Storage

Raw event, JSON on the wire                        ~500 bytes
Raw event, Parquet + ZSTD in the lake              ~80 bytes   (6× compression)

Raw per day    = 7.2e9 × 80 B                      = 576 GB/day
Raw per year                                       = 210 TB/year
Raw retention 13 months                            ≈ 228 TB

Trips per day  = 200,000 devices × 4 trips         = 800,000 rows/day
Trip row (enriched)                                ~400 bytes
Trips per day                                      = 320 MB/day
Trips per year                                     = 117 GB/year        <- tiny

Safety events  ≈ 2% of trips × 3 events            = 48,000 rows/day
Refined layer total                                ≈ 130 GB/year
The crucial ratio: raw is 210 TB/year, refined is 130 GB/year — a 1,600× reduction. This is the single most important number in the design. It means the serving layer never touches the raw volume, and ClickHouse only ever holds gigabytes, not terabytes. A single node is genuinely sufficient.

Sanity check the whole thing. 7.2B events/day is large. 130 GB/year of refined data is small. The pipeline's entire job is that reduction. If the serving layer is ever asked to scan raw volume, the design has failed — that is exactly the trap Option A (querying Iceberg in place) walks into.

Serving — ClickHouse MergeTree

CREATE TABLE trips_serving
(
    company_id      UInt32,
    start_date      Date,
    device_id       LowCardinality(String),
    driver_id       LowCardinality(String),
    trip_id         UUID,
    start_time      DateTime64(3)  CODEC(DoubleDelta, ZSTD(1)),
    duration_s      UInt32         CODEC(T64, ZSTD(1)),
    distance_km     Float32        CODEC(Gorilla, ZSTD(1)),
    max_speed_kph   Float32,
    safety_score    Float32,
    n_harsh_brake   UInt16         CODEC(T64, ZSTD(1)),
    _version        DateTime
)
ENGINE = ReplacingMergeTree(_version)
PARTITION BY toYYYYMM(start_date)
ORDER BY (company_id, start_date, device_id, start_time)
TTL start_date + INTERVAL 90 DAY;
Every line of that ORDER BY is a deliberate decision.
company_id first — every customer query filters on it, so the sparse index prunes to one tenant's granules immediately. This is the single highest-value choice in the whole serving layer.
start_date second — the near-universal second filter.
ReplacingMergeTree(_version) — late corrections arrive as an insert, not an UPDATE. Mutations rewrite whole parts; appends are cheap.

Rollups via materialized view

CREATE TABLE daily_fleet_summary (
    company_id UInt32, day Date,
    trips UInt64, total_km Float64, harsh_brakes UInt64,
    avg_safety AggregateFunction(avg, Float32)
) ENGINE = SummingMergeTree ORDER BY (company_id, day);

CREATE MATERIALIZED VIEW mv_daily TO daily_fleet_summary AS
SELECT company_id, start_date AS day,
       count() AS trips, sum(distance_km) AS total_km,
       sum(n_harsh_brake) AS harsh_brakes, avgState(safety_score) AS avg_safety
FROM trips_serving GROUP BY company_id, day;
Measured on comparable data: a rollup like this reduces 43M rows to ~6K and cuts query time from 45 ms to 2 ms — a 22× speedup on a table 17,000× smaller. The fleet-summary dashboard tile never touches the trip-level table.

5 Ingestion — Kafka

Topic design

DecisionChoiceReasoning
Partition keydevice_idGuarantees per-device ordering, which trip sessionisation requires. Also makes Flink's keyBy(device_id) a local no-op instead of a network shuffle.
Partition count64250K/s ÷ ~10 MB/s per partition = 32 minimum; 64 gives headroom and consumer parallelism. Effectively permanent — increasing it breaks key affinity.
Replication3, min.insync=2Survives one broker loss with no data loss
Retention7 daysThe replay window. Longer than the worst realistic outage.
Produceracks=all, idempotentNo duplicates from broker-side retries
Compressionzstd~4× on JSON telemetry
Partition count is a permanent decision. Increasing partitions changes the key→partition mapping, which breaks per-device ordering and corrupts any downstream keyed state. Size for peak plus growth on day one.

Handling device clock skew

Devices have unreliable clocks. Carry both timestamps: event_time from the device and ingest_time from the broker. Window on event time, but reject events whose event_time is more than 24 hours from ingest_time — those are clock faults, not late data, and they will otherwise poison your watermarks.

6 Processing — Flink

The job graph

KafkaSource(device_events)
   │  watermark: bounded out-of-orderness 2 min, withIdleness 1 min
   ▼
Validate + drop clock-fault events            [stateless]
   ▼
Deduplicate by event_id, 10-min TTL           [keyed state]
   ▼
keyBy(device_id)
   ├──▶ SessionWindow(gap 5 min) ──▶ Trip aggregation      [large state]
   └──▶ ProcessFunction ──────────▶ Safety event detection [timers]
   ▼

   ▼
   ├──▶ IcebergSink  bronze (raw passthrough)
   └──▶ IcebergSink  silver (trips, safety events)

State sizing — the number that decides your cluster

Concurrent open trips        200,000 devices × ~25% active   = 50,000
State per open trip          route points + running aggregates ≈ 8 KB
Trip session state                                             = 400 MB
Dedup state  (event_id, 10 min TTL)
   83,000/s × 600 s × 40 B                                     = 2.0 GB
Broadcast metadata (vehicles, drivers, companies)              = 200 MB
────────────────────────────────────────────────────────────────────
Total keyed state                                              ≈ 2.6 GB
2.6 GB is comfortably RocksDB territory with incremental checkpointing. Use EmbeddedRocksDBStateBackend, not heap — heap state at this size makes checkpoints slow and GC pauses visible. Incremental checkpoints mean cost scales with changed keys, not total state.

Configuration that matters

parallelism64 — matches Kafka partitions exactly, so the source is a 1:1 assignment
checkpointing.interval30 s, EXACTLY_ONCE, unaligned — completes even under backpressure
state.backendRocksDB + incremental checkpoints to S3
watermark2 min out-of-orderness, withIdleness(1 min)
session gap5 min of no movement ends a trip
Iceberg sink commitEvery 60 s — balances file size against freshness
withIdleness is not optional. Flink takes the minimum watermark across all input partitions. If one Kafka partition goes quiet — a regional outage, a fleet parked overnight — the watermark stops advancing, windows never fire, and output silently stops while the job reports healthy. It is the most common Flink production incident.
Trip sessionisation has an unbounded-state failure mode. A device that emits one event and then vanishes (crash, connectivity loss) leaves an open session forever. Guard with a maximum trip duration timer — force-close and emit any session exceeding 24 hours.

7 Storage — S3 Tables / Iceberg

Why Iceberg and not plain Parquet

Plain Parquet folderIceberg table
"The table" is whatever files are presentManifests name exactly which files are current
A failed write leaves visible garbageAtomic commits — readers never see partial writes
No schema evolution safetyColumn add/rename/reorder without rewriting
No time travelSnapshot isolation and rollback
Manual compactionS3 Tables compacts automatically

Layout

s3://lake/
├── bronze/device_events/     partitioned by days(event_time)   576 GB/day
├── silver/trips/             partitioned by days(start_time)   320 MB/day
├── silver/safety_events/     partitioned by days(event_time)
└── gold/daily_metrics/       partitioned by month              small
The streaming small-file problem. Flink committing every 60 s with parallelism 64 produces 64 files/minute = 92,000 files/day in bronze. That destroys read performance — listing overhead, task overhead, footers exceeding data.

Three mitigations, in order: (1) S3 Tables automatic compaction — the main reason to use it; (2) raise the sink commit interval to 2–5 min for bronze where freshness matters less; (3) a scheduled compaction job as a backstop.

Retention and cost management

Bronze     13 months, then expire partitions
           Lifecycle: Standard → Standard-IA at 30 days → Glacier IR at 90 days
Silver     7 years, stays in Standard (small, and read constantly)
Snapshots  expire after 7 days — otherwise metadata grows unbounded
           and every read pays to reconstruct it

                  (replication metadata)

NO SHARDING. 37 GB working set fits one node many times over.
Replicas exist for CONCURRENCY and AVAILABILITY, not capacity.
Replicas, not shards — and this is the most commonly misunderstood decision. Sharding solves "the data will not fit". Replicas solve "there are too many concurrent queries". At 37 GB with 200 concurrent users, the constraint is unambiguously concurrency. Sharding here would add operational cost, cross-shard query coordination, and a permanent, hard-to-reverse sharding key — for no benefit.

Node sizing

Per replica:  16 vCPU · 64 GB RAM · 500 GB NVMe
              working set (37 GB) fits in page cache with headroom
3 replicas across availability zones

Concurrency tuning — the setting that makes 200 users work

SET max_threads = 4;                    -- one query must NOT eat all 16 cores
SET max_execution_time = 10;
SET max_memory_usage = 8000000000;
SET max_concurrent_queries = 100;       -- per node

By default a single ClickHouse query grabs every core. For a dashboard workload you deliberately cap it, trading single-query latency for concurrent throughput.

Incremental load from Iceberg

-- every 5 minutes
INSERT INTO trips_serving
SELECT * FROM lake.trips
WHERE _iceberg_snapshot_id > (SELECT max(last_snapshot) FROM _load_watermark)
  AND start_date >= today() - 90;

Depends on the refined layer being append-only or version-stamped. Because Flink emits late corrections as new rows with a higher _version, ReplacingMergeTree collapses them on merge. Read with FINAL, or accept eventual dedup for rollups.

9 The Option A / Option B decision

OPTION A — query Iceberg in placeOPTION B — materialise into MergeTree
CREATE DATABASE lake
ENGINE = DataLakeCatalog
SETTINGS catalog_type='glue',
         region='us-east-1';

SELECT ... FROM lake.trips
WHERE company_id = 42;
 
CREATE TABLE trips_serving (...)
ENGINE = ReplacingMergeTree(_version)
ORDER BY (company_id, start_date,
          device_id, start_time);

-- + 5-minute incremental load
✓ No duplicate storage, no sync job
✓ S3 remains the only copy
✓ Always current — no freshness lag
✗ No ClickHouse sparse index
✗ Cold S3 reads on every query
✗ Concurrency multiplies S3 requests		 ✓ Sparse index, codecs, projections, MVs
✓ Millisecond queries at high concurrency
✓ Predictable latency
✗ Duplicate storage (37 GB — trivial)
✗ A sync job to build and monitor
✗ Freshness lag that must be published

The evidence

Measured on a single laptop core, 43M rows:
Full aggregation over 43M rows0.033 s
Filter on the ORDER BY prefix0.002 s — 330 of 5,284 granules read, 94% skipped
Same query via materialized view0.002 s — 22×, from a 54 KB rollup instead of an 896 MB scan
None of that is available in Option A. Querying Iceberg in place gives you only Iceberg partition pruning — no sparse index, no codecs, no projections, no MVs.

Decision

Option B for serving. Option A retained for the cold tail.

The p99 < 500 ms at 200 concurrent requirement rules out cold S3 reads per query. The duplicate storage objection evaporates once you notice the serving set is 37 GB, not 210 TB.

But keep Option A configured for queries older than 90 days. Recent data in MergeTree, history queried in place through the Glue catalog. One system, two access paths, no separate archive.
Still POC Option A first — and benchmark at real concurrency, not single-query. A single Iceberg query may look acceptable. Two hundred of them against S3 will not. The failure mode only appears under load, so a single-query benchmark will mislead you into the wrong architecture.

10 API & multi-tenancy

Request path

Customer browser
   ▼  JWT (contains company_id)
GraphQL / Cube API
   ▼  inject company_id — NEVER from a client parameter
Query cache (Redis, 60 s TTL)
   ▼  miss
ClickHouse load balancer → replica
   ▼
MergeTree or materialized view
Tenant isolation is the highest-severity risk in the system. A single missing company_id predicate leaks one customer's fleet data to another. Three layers of defence:
  1. Derive company_id from the JWT server-side. Never accept it as a query parameter.
  2. ClickHouse row policy as a backstop:
    CREATE ROW POLICY tenant ON trips_serving USING company_id = getSetting('SQL_tenant') TO api_user;
  3. Automated test that asserts every API query plan contains a company_id filter.

Caching strategy

ClickHouse query cacheIdentical queries, seconds. Free.
Redis, 60 s TTLDashboard tiles. Key includes company_id. Absorbs the refresh stampede.
Materialized viewsNot a cache — pre-computation. The real win.

Cache TTL must be shorter than the freshness SLA, or you promise 10-minute data and serve 20-minute data.

11 Failure modes & recovery

FailureBlast radiusMitigation & recovery
Kafka broker lossNoneRF=3, min.insync=2. Automatic leader election.
Flink job crashIngest stallsRestart from the last checkpoint (≤30 s of reprocessing). Kafka's 7-day retention is the buffer.
Flink state corruptionHoursRestore from an older checkpoint or savepoint. Replay from Kafka. This is why 7-day retention exists.
S3 unavailableWrites stallFlink backpressures into Kafka, which buffers. Serving continues from ClickHouse.
ClickHouse replica downNoneLB removes it. Remaining replicas absorb load. Size for N−1.
All ClickHouse downDashboards downRebuild from Iceberg. 90 days ≈ 30 GB ≈ under an hour. Lake is the source of truth.
Bad deploy of Flink logicCorrupt refined dataIceberg snapshot rollback, then replay from Kafka with fixed logic.
Idle Kafka partitionSilent output stopwithIdleness. Alert on watermark lag, not just job health — the job reports healthy while producing nothing.
Unbounded Flink stateOOM in days/weeksState TTL, max-trip-duration timers, and alert on state size trend.

What to actually monitor

INGEST     Kafka consumer lag · producer error rate
FLINK      watermark lag  ◀── the leading indicator, monitor this first
           checkpoint duration and failures
           state size trend  ◀── monotonic growth predicts death weeks ahead
           backpressure per operator
LAKE       files per partition (small-file detection) · commit latency
SERVING    ClickHouse p50/p95/p99 · concurrent queries · parts count
           incremental load lag  ◀── the freshness SLA
API        p99 by endpoint · cache hit rate · 5xx rate
BUSINESS   trips/hour vs 7-day baseline  ◀── catches silent pipeline failure
The last one matters most. Every technical metric can look healthy while the pipeline produces nothing — an idle-partition watermark stall does exactly this. A business-level volume check against baseline is the only alert that catches silent failure.

Where the money actually goes — and the levers

Bronze S3 storage (~22%)The biggest single line. Lever: aggressive lifecycle to Glacier IR, and question whether 13 months of raw is genuinely required.

The efficiency headline for the architecture review: serving costs ~12% of the platform because the pipeline reduces 210 TB/year to 130 GB/year before anything reaches the serving layer. Redshift Spectrum was scanning the lake per query; ClickHouse scans a 37 GB indexed working set.

13 Migration plan

PHASE 1 · Plumbing            2 weeks
  Stand up ClickHouse (3 replicas + Keeper)
  Configure DataLakeCatalog → Glue → verify it can read Iceberg
  Build the incremental load job with snapshot watermarks
  EXIT: ClickHouse returns correct row counts vs the lake

PHASE 2 · Benchmark            1 week
  POC Option A at REAL CONCURRENCY (50, 100, 200 clients)
  Benchmark Option B on the same query set
  EXIT: a documented latency/concurrency curve for both

PHASE 3 · One dashboard        2 weeks
  Pick the highest-traffic dashboard
  Build MergeTree tables + materialized views for it only
  EXIT: p99 < 500 ms at production concurrency

PHASE 4 · Parity harness       2 weeks  ◀── the gate
  Automated job: same query set against Redshift AND ClickHouse
  Compare per-tenant row counts and aggregates, diff → alert
  EXIT: green for 14 consecutive days

PHASE 5 · Cut over             4 weeks
  Migrate dashboards one at a time behind a feature flag
  Redshift stays warm for instant rollback
  EXIT: all traffic on ClickHouse

PHASE 6 · Decommission         1 week
  Migrate the remaining Redshift materialized views
  Snapshot, then delete the cluster
                                ───────
                        TOTAL:  12 weeks
Phase 4 is the gate, and it is non-negotiable. The parity harness is what converts "we think ClickHouse is right" into "we have 14 days of evidence that the numbers match." Without it, the first customer-reported discrepancy after cutover becomes an argument rather than a diagnosis.

Rollback at every phase

Redshift stays operational until phase 6. Every dashboard cutover is behind a feature flag, so rollback is a config change, not a redeploy. Nothing in phases 1–5 is irreversible.

Known limitations of this design

  • 90-day serving window. Queries beyond it fall back to Option A and are slower. Acceptable because dashboard usage is overwhelmingly recent, but it must be communicated, not discovered.
  • ~10 minute freshness. Not real-time. If a customer needs sub-minute, that requires a separate Kafka → ClickHouse path with explicitly different semantics.
  • Single-region. Multi-region adds cross-region replication cost and consistency questions not addressed here.
  • Late corrections beyond 90 days update Iceberg but not the ClickHouse serving table. Needs either a periodic reconciliation job or an accepted staleness boundary.

The three sentences for the architecture review

1. S3 Tables remains our durable, open-format system of record; Flink owns the canonical transformation logic and produces refined Iceberg tables.

2. We validate ClickHouse's native Glue/Iceberg access first — but we expect it to miss customer-facing concurrency SLOs, and the POC sets the boundary of where in-place querying remains useful.

3. ClickHouse becomes the serving layer by incrementally materialising the refined dataset into native MergeTree; Redshift is a migration bridge and is retired after 14 days of automated parity.

Capacity figures are estimates from the stated assumptions — 200K devices, 1 event/sec, 10 active hours. ClickHouse timings measured on a single laptop core against 43M rows. Costs are US-East list-price approximations and will vary with commitment discounts.
