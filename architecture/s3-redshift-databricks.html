The whole picture

One bucket, two consumption models: copy-in versus query-in-place.

Path 1 — S3 Parquet into Redshift

The COPY command

-- 1. table must exist first
CREATE TABLE trips (
    vendor_id      INTEGER,
    pickup_ts      TIMESTAMP,
    dropoff_ts     TIMESTAMP,
    trip_distance  DOUBLE PRECISION,
    fare_amount    DOUBLE PRECISION,
    pu_location_id INTEGER
)
DISTKEY (pu_location_id)      -- how rows spread across compute nodes
SORTKEY (pickup_ts);          -- how rows are ordered within a node

-- 2. load
COPY trips
FROM 's3://naveen-data-lab-457360056131/raw/taxi/'
IAM_ROLE 'arn:aws:iam::457360056131:role/RedshiftS3Read'
FORMAT AS PARQUET;
Why COPY and not INSERT. COPY loads in parallel across every slice of the cluster at once. Row-by-row INSERT goes through the leader node single-threaded and is orders of magnitude slower. Never use INSERT for bulk loads.

The IAM role — the part that trips people up

Trust policy    : allows redshift.amazonaws.com to assume the role
Permissions     : s3:GetObject + s3:ListBucket on your bucket
Then            : attach the role to the Redshift cluster/namespace

Redshift does not use your credentials. It assumes a role. If COPY fails with Access Denied, it is almost always the trust policy or a missing s3:ListBucket on the bucket ARN (not just the object ARN).

Alternative: Spectrum — no copy at all

CREATE EXTERNAL SCHEMA spectrum_schema
FROM DATA CATALOG DATABASE 'my_glue_db'
IAM_ROLE 'arn:aws:iam::457360056131:role/RedshiftS3Read';

SELECT * FROM spectrum_schema.trips WHERE pickup_date = '2024-01-15';

Redshift queries the Parquet in S3 directly via the Glue Data Catalog. No storage cost in the cluster, but each query pays S3 read latency. Good for cold/archive data, weak for high-concurrency dashboards.

Path 2 — Databricks Delta tables in the same bucket

Writing the table

# Databricks notebook
(df.write
   .format("delta")
   .mode("overwrite")
   .partitionBy("pickup_date")
   .save("s3://naveen-data-lab-457360056131/delta/trips"))

# or as a catalog-registered table
df.write.format("delta").saveAsTable("main.default.trips")

What _delta_log actually does

Without it (plain Parquet)With it (Delta)
A folder of files. "The table" = whatever files happen to be there. The log lists exactly which files belong to each version.
A failed write leaves half-written garbage readers can see. Commits are atomic — readers never see a partial write.
No UPDATE / DELETE / MERGE. Full MERGE INTO, UPDATE, DELETE.
No history. Time travel: VERSION AS OF 3.
Schema drift silently corrupts data. Schema enforced on write.
The mental model: Delta = Parquet + a folder of JSON commits. Nothing proprietary, nothing locked in. Delete _delta_log and you still have readable Parquet — you just lose ACID, history and the ability to know which files are current.

Who does what

PrefixWritten byRead by
raw/Ingest jobs, Flink, CLI uploadRedshift COPY · Databricks · Athena · Glue
delta/Databricks onlyDatabricks · Athena (via manifest) · Trino
curated/Databricks / GlueRedshift Spectrum · Athena · BI tools
One writer per prefix. Never let two systems write the same Delta table folder. Delta's ACID guarantees rely on a single coordinated writer protocol; a stray Spark job or a manual S3 upload into delta/trips/ will corrupt the table's view of itself.

IAM — the two roles you need

RedshiftS3Read              (assumed by Redshift)
  trust : redshift.amazonaws.com
  allow : s3:GetObject     on  arn:aws:s3:::naveen-data-lab-457360056131/raw/*
          s3:ListBucket    on  arn:aws:s3:::naveen-data-lab-457360056131

DatabricksS3Access          (assumed by Databricks, cross-account)
  trust : Databricks' AWS account + external ID
  allow : s3:GetObject, s3:PutObject, s3:DeleteObject, s3:ListBucket
          on the whole bucket (Delta needs write + delete for compaction)
s3:ListBucket must be granted on the bucket ARN, not the object ARN. Granting it only on bucket/* is the single most common cause of a mysterious Access Denied during COPY.

Choosing between the two paths

QuestionRedshift (COPY)Databricks (Delta on S3)
Where does data live?Inside the cluster (a 2nd copy)Only in S3 (one copy)
Query latencyLowest — local columnar storageGood, but reads from S3
ConcurrencyExcellent for BIGood; scales by adding compute
Cost when idleCluster keeps runningZero — turn compute off, data stays
Other engines can read itNoYes — open Parquet format
Best forBI dashboards, SQL analystsETL, ML, big transforms, data lake
They are not competitors here. The common pattern is: Databricks does the heavy transformation and writes curated Parquet/Delta to S3; Redshift COPYs (or Spectrum-queries) the small curated result for BI. S3 is the shared, durable middle.

The end-to-end flow, in words

  1. Source systems drop Parquet into s3://.../raw/
  2. Databricks reads raw/, cleans and joins it, writes Delta to delta/ — data files and _delta_log side by side in the same bucket
  3. Databricks writes a small aggregated result to curated/ as plain Parquet
  4. Redshift COPYs curated/ into cluster tables for BI, or reads it in place via Spectrum
  5. Dashboards query Redshift; data scientists query Delta from Databricks. One bucket, one copy of the truth.
