URL Shortener

End-to-end system design. The classic interview problem, done properly — capacity math, the key-generation decision, storage, caching, analytics, and the trade-offs that actually get probed.

ProblemTurn a long URL into a short one. Redirect on access. Track clicks.
Scale100M new URLs/day · 10B redirects/day · 100:1 read:write
Hard parts(1) Generating unique short codes at 1,160/sec without collisions. (2) Serving 350K redirects/sec at p99 < 50 ms. (3) Analytics without slowing the redirect.
ShapeOverwhelmingly read-heavy KV lookup. That single observation drives every storage and caching decision.

The one insight that structures the whole answer. This is not a hard computation problem — it is a hard lookup at scale problem. Reads outnumber writes 100:1, the access pattern is a single key lookup with no joins, and the data is immutable once written. That means: NoSQL over relational, cache-first, and a code-generation scheme that avoids coordination.

1 Requirements

Functional

F1Given a long URL, return a short URL
F2Given a short URL, redirect to the original
F3Optional custom alias — short.ly/my-campaign
F4Optional expiry — default 5 years, user-settable
F5Click analytics — count, timestamp, referrer, geo, device
F6Users can list and delete their own links

Non-functional

RequirementTargetConsequence
Redirect latencyp99 < 50 msA redirect sits in the critical path of a page load. Forces cache-first.
Availability99.99% for redirectsA dead link is worse than a slow one. Redirects matter more than creates.
Creation latencyp99 < 200 msInteractive but not critical-path
DurabilityNo lost mappingsA lost mapping breaks every link ever shared
UniquenessNo collisions, everA collision sends a user to the wrong site — a security issue, not a bug
UnpredictabilityCodes not enumerableSequential codes let anyone scrape every link
Scale10B reads/day~116K/sec average, ~350K/sec peak
Availability > consistency here. If a newly created short link takes two seconds to become visible in every region, nobody notices. If a redirect fails, a shared link is broken and the user blames the brand that shared it. This is an AP system in CAP terms — and saying so, with that justification, is the point.

Out of scope

  • Link preview / unfurling · A/B split-testing destinations · QR generation
  • Editing a destination after creation — mappings are immutable (see §6 for why that matters)

2 Capacity estimation

Traffic

New URLs per day                   100,000,000
Read : write ratio                       100 : 1
Redirects per day                   10,000,000,000

Writes/sec  = 100e6 / 86,400              ≈ 1,160/sec
Reads/sec   = 10e9  / 86,400              ≈ 116,000/sec
Peak (3×)                                 ≈ 350,000/sec

How long must the short code be?

Alphabet: base62  [a-z A-Z 0-9]

62^5 =            916 million      ← 9 days of capacity. No.
62^6 =         56.8 billion        ← 1.5 years. No.
62^7 =        3,521 billion        ← 96 years at 100M/day.  ✓
62^8 =      218,000 billion        ← overkill, wastes 1 char

→ 7 characters.  short.ly/aX9k2Bq
Do this calculation out loud in an interview. It is the single most expected piece of arithmetic in this problem, and picking 7 without showing why 6 fails is a missed signal.

Storage

Per record
   short_code       7 B
   long_url       ~200 B  (average; cap at 2 KB)
   user_id         16 B
   created_at       8 B
   expires_at       8 B
   metadata       ~60 B
   ─────────────────────
   ≈ 300 B, call it 500 B with index overhead

Per day    100e6 × 500 B                  = 50 GB/day
Per year                                  = 18 TB/year
5 years                                   = 91 TB
With replication (×3)                     = 273 TB

Bandwidth & memory

Write  1,160/s × 500 B                    = 0.6 MB/s     trivial
Read   116,000/s × 500 B                  = 58 MB/s      modest

CACHE SIZING — apply the 80/20 rule
  20% of URLs generate 80% of traffic.
  Cache the hot 20% of one day's reads:
     10e9 × 20%  = 2e9 requests → but distinct URLs are far fewer.

  Practical approach: cache ~20% of daily-active distinct URLs
     ~100e6 distinct hot URLs × 500 B    ≈ 50 GB
  → a modest Redis cluster. Target 90%+ hit rate.
Notice what the numbers say. Writes are trivial (1,160/sec — a single Postgres box could do it). Storage is large but not exotic. The entire difficulty is 350K reads/sec at p99 < 50 ms. That is a caching and horizontal-read-scaling problem, and the design should say so explicitly rather than treating all three dimensions as equally hard.

3 API design

POST /api/v1/urls
  Authorization: Bearer <token>
  {
    "long_url":     "https://example.com/some/very/long/path?a=1",
    "custom_alias": "my-campaign",        // optional
    "expires_at":   "2027-01-01T00:00:00Z" // optional
  }
  → 201 Created
  {
    "short_url":  "https://short.ly/aX9k2Bq",
    "short_code": "aX9k2Bq",
    "long_url":   "https://example.com/...",
    "expires_at": "2031-08-11T00:00:00Z"
  }
  → 409 Conflict        custom alias already taken
  → 400 Bad Request     malformed or blocked URL
  → 429 Too Many        rate limited

GET /{short_code}
  → 302 Found
    Location: https://example.com/some/very/long/path?a=1
    Cache-Control: private, max-age=0
  → 404 Not Found       unknown or expired
  → 410 Gone            deleted by owner

GET  /api/v1/urls/{short_code}/stats     → click analytics
GET  /api/v1/urls?user_id=…&cursor=…    → list, cursor-paginated
DELETE /api/v1/urls/{short_code}          → 204, soft delete

Rate limiting

Anonymous create10 / hour / IP
Authenticated create1,000 / day / user
RedirectNot limited — it is the product

Token bucket in Redis, keyed by IP or user. Return 429 with Retry-After.

Why the redirect endpoint is not versioned or namespaced. GET /{short_code} lives at the root because every character counts — that is the entire product. The consequence is a namespace collision risk with real routes: /api, /login, /health. Maintain a reserved-words blocklist and exclude those strings from generation.

4 Key generation — the core problem

Everything else in this design is standard. This is the decision the interview is actually about.

Option A — Hash the URL, truncate

code = base62( md5(long_url) )[:7]
✓Stateless. Same URL always yields the same code — natural deduplication.
✗Collisions are certain. Birthday paradox: with 3.5e12 space, expect the first collision around √(3.5e12) ≈ 1.9M URLs. At 100M/day that is every few minutes.
✗Resolving a collision needs a read-before-write, which is a round trip on the hot path.

Option B — Global counter, base62 encoded

code = base62( atomic_increment(counter) )
✓Zero collisions by construction. Compact.
✗Enumerable. Code N implies N−1 exists. Anyone can scrape every link ever created — a serious privacy failure.
✗The counter is a single point of contention at 1,160 writes/sec.

Option C — Key Generation Service (pre-generated keys)

A separate service pre-generates random unique 7-char keys offline
and stores them in two tables:  unused_keys  |  used_keys

App servers claim a BLOCK of ~1,000 keys at a time, hold them in
memory, and hand them out with no per-request coordination.
✓No collisions — uniqueness is guaranteed at generation time
✓Not enumerable — keys are random
✓No coordination on the hot path. Key assignment is a memory read
✗Another service to run. Keys are lost if a server dies mid-block (acceptable — the space is 3.5 trillion)

Option D — Distributed ID (Snowflake) + base62

64-bit ID = [41 bits timestamp][10 bits machine][12 bits sequence]
code = base62(id)   → but this is 11 chars, and time-ordered = enumerable
Fix by XOR-ing with a secret, or Feistel-permuting the ID space.
Recommendation: Option C, the Key Generation Service. It is the only design that gets all three properties simultaneously — collision-free, unpredictable, and coordination-free on the write path. Hashing fails on collisions, counters fail on enumerability, and Snowflake needs an extra permutation step to fix ordering.

Being able to articulate why the other three fail matters more than naming the winner.

Custom aliases

Custom aliases bypass the KGS entirely and go straight to a
conditional insert:

   PutItem(short_code = 'my-campaign',
           ConditionExpression = 'attribute_not_exists(short_code)')

→ 409 Conflict on failure.
Validate against the reserved-words blocklist first.

5 High-level architecture

Cache-first read path · KGS removes coordination from the write path · analytics is fully async.

6 Data model & storage

Why NoSQL, not a relational database

Property of this workloadConsequence
Single-key lookup, no joinsRelational features are unused overhead
Records immutable after writeNo update contention, no transaction needs
91 TB, growing 18 TB/yearMust shard. NoSQL does it natively; RDBMS needs manual sharding
350K reads/secHorizontal read scale is the whole requirement
Availability > consistencyEventual consistency is acceptable and cheaper
DynamoDB or Cassandra. The access pattern is literally a key-value get. A relational database would work at small scale and become the bottleneck at this one — and you would spend your time building the sharding layer that DynamoDB gives you for free.

Schema

TABLE urls
  short_code    STRING   ← PARTITION KEY.  High cardinality, uniform
                            distribution → no hot partitions by design
  long_url      STRING
  user_id       STRING
  created_at    NUMBER
  expires_at    NUMBER   ← DynamoDB TTL: automatic deletion, no cron job
  is_deleted    BOOL
  click_count   NUMBER   ← denormalised, updated async

GSI  user_id-created_at-index    → "list my links", cursor paginated
The partition key choice is the entire scalability story. short_code is random base62, so keys distribute perfectly uniformly across partitions. There is no hot key, no rebalancing, no resharding — by construction, not by tuning. Contrast with partitioning by user_id, where one viral account would melt a single partition.

Why mappings are immutable

Allowing a destination to be edited turns a shortener into a redirect-hijacking tool — share a link to a news article, then repoint it at malware after it has spread. Immutability is a security decision, not a simplification. Deletion is a soft delete returning 410 Gone.

Sharding, if using Cassandra rather than a managed store

shard = consistent_hash(short_code) % N

Consistent hashing so adding a node moves ~1/N of keys, not all of them.
Replication factor 3, spread across availability zones.
Reads at CL=ONE (fast, eventually consistent — correct for this workload).

7 Caching

The read path

GET /aX9k2Bq
   │
   ▼  1. Redis GET aX9k2Bq
   ├── HIT  (90%+)  → return 302 immediately          ~1 ms
   │
   └── MISS
        ▼  2. DynamoDB GetItem(short_code)            ~10 ms
        ├── found   → SETEX into Redis, return 302
        └── missing → 404, and cache the negative result briefly

Cache design decisions

EvictionLRU. Access is strongly recency-correlated — a link goes viral, then dies. LRU matches that shape exactly.
TTL24 hours. Entries are immutable, so a long TTL is safe. TTL exists to bound memory, not for correctness.
Size~50 GB across a Redis cluster. Sized from the 80/20 estimate in §2.
Negative cachingCache 404s for ~60 s. Otherwise a scanner probing random codes drives 100% cache misses straight into the database.
WarmingPre-populate on create — the creator is likely to click it first.
Two failure modes to name unprompted.

Cache stampede. A viral link expires from cache; 50,000 concurrent requests all miss and hit the database simultaneously. Fix: request coalescing (single-flight) — the first miss fetches, the rest wait on that one promise.

Cold-start thundering herd. A Redis node restarts empty and the full read load lands on DynamoDB. Fix: replicas, gradual traffic ramp, and a database provisioned to survive a period of low hit rate.

CDN edge caching

A 302 with a short Cache-Control can be cached at the CDN edge for the hottest links, absorbing traffic before it reaches your infrastructure at all. The trade-off is analytics fidelity — edge-cached redirects are invisible to you unless the CDN streams its logs back. For a link that is being shared millions of times an hour, that trade is usually worth it.

8 The redirect — 301 vs 302

A small question that reveals whether someone has thought about the product.

301 Moved Permanently302 Found (or 307)
Browser behaviourCaches the redirect. Subsequent clicks never reach your serverAsks your server every time
Your trafficDramatically lowerFull load — every click
AnalyticsBroken. You see the first click and nothing afterComplete
ReversibilityEffectively permanent — cached in browsers you cannot reachFully reversible
SEOPasses link equity to the destinationDoes not
Use 302 (or 307). Click analytics is a core feature — F5 in the requirements — and 301 destroys it. The deeper reason is reversibility: if a link is later found to point at malware, a 301 is cached in millions of browsers you have no way to reach. With 302 you disable it and the next click is blocked.

307 over 302 if method preservation matters — 302 historically allowed clients to convert POST to GET; 307 forbids it. For a link shortener the distinction rarely bites, but knowing it is the difference between a memorised answer and an understood one.
HTTP/1.1 302 Found
Location: https://example.com/some/very/long/path
Cache-Control: private, no-store        ← stop intermediaries caching it
Referrer-Policy: unsafe-url             ← preserve referrer for the destination
X-Content-Type-Options: nosniff

9 Analytics pipeline

The critical constraint: analytics must never slow the redirect. At 350K/sec, a synchronous write per click would double your latency and couple redirect availability to analytics availability. Fire-and-forget into a queue, always.
Redirect service
   │  emit click event, non-blocking, ~0.1 ms
   ▼
KAFKA  topic: click_events, partitioned by short_code
   │     { short_code, ts, ip, user_agent, referrer, country }
   ▼
Stream processor  (Flink / Kafka Streams)
   ├─▶ enrich: IP → geo, UA → device/browser
   ├─▶ bot filtering
   └─▶ windowed aggregation
   ▼
ClickHouse
   ├── clicks_raw        90-day retention, per-event
   └── clicks_hourly     materialized view rollup, kept forever

ClickHouse schema for the analytics side

CREATE TABLE clicks_hourly (
    short_code  String,
    hour        DateTime,
    country     LowCardinality(String),
    device      LowCardinality(String),
    clicks      UInt64
) ENGINE = SummingMergeTree
ORDER BY (short_code, hour, country, device);

CREATE MATERIALIZED VIEW mv_hourly TO clicks_hourly AS
SELECT short_code, toStartOfHour(ts) AS hour, country, device, count() AS clicks
FROM clicks_raw GROUP BY short_code, hour, country, device;

ORDER BY leads with short_code because every stats query filters on it — the sparse index prunes to one link's granules immediately.

The denormalised click counter

Do NOT increment click_count in DynamoDB on every redirect —
that turns an immutable record into a hot write at 350K/sec.

Instead: a stream consumer batches counts and updates DynamoDB
every ~60 s. The counter is approximate and eventually consistent.
Exact counts come from ClickHouse when asked.
Bot traffic is 30–50% of clicks on a real shortener. Filtering it in the stream — user agent, request patterns, known crawler IP ranges — is a product requirement, not a nicety. Reporting inflated numbers to a customer is worse than reporting nothing.

What to monitor

REDIRECT   p50/p99 latency · 4xx and 5xx rate · requests/sec
CACHE      hit rate  ◀── the leading indicator. Below 85% = investigate now
DATABASE   read/write capacity consumed · throttles · p99
KGS        available key buffer  ◀── alert at 20%, creates fail at 0
ANALYTICS  Kafka consumer lag · events dropped
BUSINESS   creates/hour and redirects/hour vs 7-day baseline
           ◀── catches silent failure that every technical metric misses
Cache hit rate is the metric to watch first. Everything downstream — database load, p99 latency, cost — is a function of it. A drop from 92% to 80% means 2.5× the database traffic, and it will show up in the hit-rate graph before it shows up as user-visible latency.

11 Security & abuse

Shorteners are an abuse magnet. They hide the destination — which is precisely what phishing and malware campaigns want. Any serious design must address this, and most candidates never mention it.

At creation time

URL validationScheme must be http/https. Reject javascript:, data:, file:
SSRF protectionResolve the host and reject private IP ranges — 127.0.0.0/8, 10/8, 169.254.169.254 (cloud metadata). Re-check after redirects.
Safe BrowsingCheck against Google Safe Browsing / PhishTank at creation
Shortener chainingReject URLs pointing at other shorteners — they defeat scanning
Reserved wordsBlock /api, /login, /admin, /health, plus offensive strings

Continuously, after creation

A URL that was clean at creation can be weaponised later — this is the standard attack. Re-scan asynchronously, prioritising links by click volume, and disable on a hit. Because the redirect is a 302, disabling takes effect on the very next click.

At redirect time

Known-bad → serve an interstitial warning page, not a redirect
Unknown   → optional interstitial for links younger than N minutes
All       → strip credentials from the URL, set Referrer-Policy

Privacy

  • Codes must be unpredictable — otherwise every link ever created is enumerable. This is why the counter approach in §4 is rejected on privacy grounds, not just aesthetics.
  • Short links are not access control. Anyone with the code has access. Say this explicitly — users routinely assume otherwise and shorten sensitive documents.
  • IP addresses in click logs are personal data. Truncate or hash, and set a retention policy.

           reads 10B/day on-demand                    ~$75,000/mo   ◀── dominant
           (reserved capacity cuts this substantially)

Compute    redirect + create services, autoscaled      ~$8,000/mo

──────────────────────────────────────────────────────────────
TOTAL                                                ~$127,000/mo
Database reads dominate — which makes cache hit rate a cost lever, not just a latency lever. Moving from 90% to 95% hit rate halves the database read bill. That single sentence reframes caching from a performance optimisation to the primary cost control, and it is the kind of observation that distinguishes a senior answer.

Trade-offs made, and when they would flip

DecisionReasoningWould change if…
NoSQL over SQLPure KV access, no joins, horizontal scale neededScale were 1000× smaller — Postgres would be simpler
KGS over hashingCollision-free and unpredictable without hot-path coordinationDeduplication of identical URLs were a hard requirement — hashing gives that free
302 over 301Analytics and revocabilityAnalytics were not a feature and cost mattered more
Async analyticsMust not couple redirect latency to analytics availabilityNever. This one is not negotiable at this scale
7-char codes96 years of headroom at 100M/dayVanity mattered more — 6 chars, accept a 1.5-year horizon and a plan
Immutable mappingsPrevents redirect hijackingNever. It is a security property

Known limitations

  • No deduplication. The same long URL submitted twice yields two codes. Adding a secondary index on hash(long_url) would fix it at the cost of a write-path lookup — usually not worth it, since users often want distinct codes for distinct campaigns.
  • Click counts are approximate in DynamoDB and eventually consistent. Exact figures come from ClickHouse.
  • Edge-cached redirects are invisible to analytics unless CDN logs are ingested.
  • No link editing, by design.

How to open the answer in an interview

"This is a read-heavy key-value lookup problem — 100:1 reads to writes, single-key access, no joins, and records that are immutable once written. So the interesting parts are how we generate codes that are unique and unpredictable without coordinating on every write, and how we serve 350K redirects a second at p99 under 50 ms. Let me size it first, then work through key generation, because that is where the real design decision lives."

Naming the shape of the problem before drawing boxes is what separates a structured answer from a recital.

Capacity figures follow the standard interview assumptions — 100M new URLs/day, 100:1 read:write. Costs are order-of-magnitude US-East estimates and vary substantially with reserved capacity and negotiated rates.
